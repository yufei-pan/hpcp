# hpcp
A simple script that can issue multiple `cp -af` commands simultaneously on a local system.

Optimized for use in HPC scenarios and featuring auto-tuning for files-per-process.

Includes an adaptive progress bar for copying tasks from multiCMD.

Tested on a Lustre filesystem with 1.5 PB capacity running on 180 HDDs. Compared to using `tar`, **hpcp** reduced the time for tarball/image release from over 8 hours to under 10 minutes.

## Development status

Basic functionality (parallel copy) should be stable.

Imaging functionality (source/destination as `.img` files) includes differential patch images (`-diff` / `-siff`, see below). Imaging is only available on Linux—similar to `tar`, but uses disk images.

Block-image functionality is in **beta**. Only available on Linux. Possible use case: cloning a currently running OS without mounting `/` as read-only.

hpcp.bat available on github: simple old tk based GUI intended for basic windows functionality.

## Upgrading to 9.87 from 9.86

Nothing needs doing to upgrade. What changed:

- **A stopped run ends:** a run stopped with Ctrl-C, SIGTERM or SIGHUP, or one whose copy worker dies, no longer waits for good on Python's process pool (9.85 hung in 9 of 3,300 early stops in the reviewer's probe on Python 3.6 and 3.14, and 9.84 about as often: a stop raised inside the pool's own lock handling, a worker stuck between files, a result a killed worker half wrote). The main process acts on a stop only between its waits, within 1 s; a worker between files that is still there 4 s after the stop is killed (it holds no temporary file); a worker in a file is waited for, so its cleanup still removes its temporary or torn file; and a pool whose worker died and that then stops answering for 4 s ends the run with exit 191 (`Copy process crashed: a pool worker died and its pool stopped answering`). A stop still exits 130 for Ctrl-C, and by its signal for SIGTERM and SIGHUP.
- **A stop Python drops is acted on:** a `KeyboardInterrupt` that Python drops in the main process (raised in a weakref callback or a `__del__`) was not acted on: during the copy the run ended with exit 191 instead of 130, and outside it the run went on to its end, a move removing its sources. The stop is recorded first and acted on at the next check: each pass of a pool loop, each file of a serial copy, and before every phase, the move's removal among them.
- **No traceback on an early Ctrl-C on Python 3.14:** a worker's stops stay blocked until hpcp's handlers are in, under every start method (3.14's forkserver too); about one early Ctrl-C in three printed a `KeyboardInterrupt` traceback before, as in 9.84. On Python 3.6 and 3.7 a stop that lands where Python drops it (a weakref callback or a `__del__`, as a thread or a pool worker goes) is recorded and acted on without the `Exception ignored` traceback Python printed for it (about one early Ctrl-C in 100 on a loaded host; 3.8 and later already hid it).
- **A second stop says how to end at once:** later stops are still ignored, so the cleanup is never cut halfway; the first of them prints `Stopping: cleaning up first (cp stopped, temporary files removed, images unmounted); Ctrl-\ ends hpcp now, which may leave them`.
- **Directories end with their source's mode and times:** a directory's times, exact mode and BSD flags are now set after what goes in it (its files, its links, `-rme`'s removals), deepest first, as `cp -a` and rsync do; its owner, xattrs and a mode that still lets its owner in come first, when it is made. 9.86 set them all before its files went in: a non-root copy of a directory of mode 0555 or 0444 holding files exited 190 with the directory empty, and every directory that got a file, a link or a subdirectory kept the copy's time until a rerun (in a probe, 3 of 7 directories on Python 3.14 and 5 of 7 on 3.6). While a non-root run copies, each of its own directories whose source mode lacks owner read, write or search is open to its owner (`u+rwx`) until the end; a stopped run leaves it so until a rerun. A clean rerun sets nothing on a directory that already matches, except those restrictive ones: two mode changes each. With `-co` directories get no metadata, as before.
- **A move writes its directories to disk:** each directory the copy synced is fsynced once its metadata is set, through the descriptor that set it (so a directory whose mode shuts its owner out is still written), and then, once each, every other directory the move wrote into: the directory of each file and link it landed (under `-nds` too) and the parent of each source's landing, in `-j` threads. All before any source is removed; one that fails is a failed copy (`Copy failed: the directory DIR cannot be written to disk (why)`, exit 212, every source kept). 9.86 fsynced only the directories it made links in: after a power cut within the journal interval an empty directory, a directory's mode, owner or times, or (outside ext4 and XFS, where a file's own fsync commits its name) a file's name could be missing with its source gone. Known: another user's directory the runner may not read (a write-only drop box) cannot be opened, so the files and links moved into it are not fsynced there (see [docs/limitations.md](docs/limitations.md)).
- **Known: a stopped run waits for a worker whose file operation never returns** (a write or fsync to a dead hard-mounted NFS server, a disk in an uninterruptible wait): hpcp prints `Waiting for N worker(s) still finishing a file (pids ...)`, and Ctrl-\ ends it at once, which can leave that worker's temporary or torn file (see [docs/limitations.md](docs/limitations.md)).

## Upgrading to 9.86 from 9.85

Nothing needs doing to upgrade. What changed:

- **A rewrite is written in place again, and keeps its inode:** a file that is already at the destination is opened by hpcp for writing (never through a link, never waiting on a FIFO) and `cp` writes that open file, as 9.84 wrote the file, so what the filesystem keeps on the inode stays: a Lustre or GPFS layout set with `lfs setstripe`, `chattr` flags, a project id; NFS readers keep reading it (no `ESTALE`, no `.nfsXXXX` for `-rme` to find). On Linux `cp` is given the worker's `/proc/PID/fd/N` for the open file, so a link put at the name during the run is never written through (asked once per worker by doing it: `cp` writing to a descriptor of `/dev/zero`); off Linux, and where that cannot work (a `cp` that is not GNU `cp`, a `/proc` of another PID namespace), `cp` gets the name, as in 9.84. Plain runs carry the source's mode, times, xattrs and SELinux label onto it (the label by hpcp, through the open file: `cp -a` sets an existing file's label by name, which the `/proc` name is not) and remove a stale `user.*` xattr; `-co` keeps the old owner, mode and xattrs. As in 9.84, a source that fails part way, a stop or a full disk can then cost the old copy (exit 190, the source kept), and a rewrite outside a move is not fsynced; a move still fsyncs every landing before any source goes.
- **Beside only where a write in place could corrupt, or with `-wb`:** a file with other names (a write in place would change them all), one that cannot be opened for writing (read-only for the runner, a running program), a source that is no regular file (a FIFO, socket or device node: `cp -a` makes it anew, which it cannot do to a file held open), anything the open finds changed since hpcp looked (never handed to `cp` by name), and a FIFO, socket, device node or link below a destination go beside and are renamed over what is there once whole, as in 9.85. `-wb` (`--write_beside`, `--write-beside`) does that for every rewrite, so a source that fails, a full disk or a stop leave the old copy as it was (exit 190), at 9.85's costs: a new inode (the layout, `chattr` flags and project id are not kept; NFS readers holding it open may get `ESTALE`), an fsync of each new copy, a new name in the file's directory and room for a second copy. The beside route never falls back to writing in place: where the new copy cannot be made, filled, written to disk or renamed over the old one, the old copy stays, exit 190, with the cause named (`... leaving DEST as it is: it has other names, which a write in place would change; the new copy beside it failed: ...`), and under `-wb` with `without -wb it would be written in place` where the default would have; a FIFO, socket, device or link that cannot be replaced is a 213, as in 9.85.
- **`-co` carries a file's ACL on XFS as root on EL7 and EL8:** there XFS lists an ACL to root under its own name (`trusted.SGI_ACL_FILE`, `trusted.SGI_ACL_DEFAULT`) as well as `system.posix_acl_*`, and hpcp took that name for an xattr it cannot carry to a new file: on the beside route a hard-linked file with an ACL got a new file without it (9.85 too), and under `-wb` every file with an ACL would have kept its old copy (190). The `system.*` name carries it now.
- **`-co`'s carry-over no longer follows a link put at the new file's name (9.85 too):** on the beside route (`-wb`, a file with other names, a source `cp` makes anew), the old copy's owner, group, xattrs and mode were set on the temporary file by its name after `cp` made it, and `chown`, `chmod` and `setxattr` follow links: in a root run into a directory another user can write, a link (or a second name of another file) put there at that moment gave that other file the old copy's owner and mode. On Linux each step now goes through a descriptor of what `cp` made, which a link or a file with another name cannot replace: it is refused (exit 190, the old copy kept). Off Linux it still goes by name (see "Off Linux, a rewrite in place can be swapped for a link mid-run" in [docs/limitations.md](docs/limitations.md)).
- **A named link the kernel refuses to follow is kept, as in 9.84:** 9.85 resolved a link that `-d` names itself and gave `cp` the resolved path, so the kernel's `fs.protected_symlinks` (another user's link in a sticky world-writable directory such as `/tmp` is refused to the one who follows it) no longer applied, and a root run wrote through a link another user had planted. 9.86 asks the kernel first: a link it refuses is kept, exit 190, `... is a link to TARGET, which cannot be followed (Permission denied)`, nothing written. This changes 9.85's behaviour for such a link (written through) back to 9.84's. A dangling link is kept, and a link in a loop replaced, as in 9.85.
- **`-rbw` (`--read_before_write`, `--read-before-write`):** before a rewrite in place, the source is read to its end; a source that fails on read leaves the old copy as it is (exit 190). It costs a second read of each rewritten file, and does nothing with `-wb`, which writes nothing in place.
- **A warning before a copy that may not fit:** where the destination's free space (`statvfs`'s `f_bavail`) is less than the source's allocated size, hpcp prints `Space warning: DIR has NB free, less than the NB that SRC needs, ...` on stderr before `cp`, saying whether the old copy can be lost, once per destination filesystem in a run, then tries, as GNU `cp` tries and fails: nothing is refused, and the exit code is the copy's (a run whose copies fit after all exits 0). The run's warnings are repeated at its end. Only on ext2/3/4, XFS and tmpfs. Missed warnings, where the free space says too little (the copy is tried as ever): btrfs, ZFS and bcachefs (compression, shared blocks), NFS, SMB, Lustre and GPFS (pooled space), overlay (it hides what is below), and an XFS with the source on the same filesystem, where `cp` may clone it (GNU `cp` 9 and later does by default; the `cp` 8.x of EL7 and EL8 never does, so there a copy that cannot fit gets no warning either, then fails). A root run onto an ext filesystem that is full for users but not for root gets one needless warning. `-enes` is unchanged.
- **A rewrite costs what it cost in 9.84 again:** 1,000 rewrites of 4 KiB files on the EL7 VM (2 vCPUs, nothing else running in it, the host busy; Python 3.6; four rounds each, the versions interleaved) took 2.79 to 3.39 s on ext4 against 9.85's 4.47 to 6.39 s and 9.84's 2.87 to 3.73 s, and 3.07 to 4.52 s on XFS against 3.75 to 7.62 s and 3.06 to 4.42 s. On a busy host (Docker, Python 3.14, XFS on NVMe, 32 threads, load about 20 to 80, default `-j`), 5,000 rewrites took 0.51 to 1.05 s (median 0.63 s) against 9.85's 0.62 to 1.53 s (0.72 s) and 9.84's 0.46 to 0.77 s (0.54 s), six rounds; 20,000 took 1.22 to 2.47 s against 1.69 to 4.42 s and 1.09 to 2.63 s, three rounds. `-wb` costs about what 9.85 cost: on the EL7 VM, in a later and busier hour, three rounds each, ext4 5.66 to 6.11 s against 9.85's 6.57 to 9.12 s (9.86's default 4.10 to 4.30 s), XFS 4.13 to 4.57 s against 4.42 to 5.12 s (3.58 to 4.74 s). Not measured on NFS.
- **Known: a source that fails part way through a rewrite costs the old copy** (truncated first, then removed), exit 190, the source kept, as in 9.84; `-rbw` or `-wb` keep it (see [docs/limitations.md](docs/limitations.md)).
- **Known: another program reading a file while it is rewritten in place sees it empty or partly written,** as with plain `cp` and in 9.84; 9.85 wrote beside and renamed, so readers saw the whole old or the whole new file. `-wb` gives them that whole-file view (see [docs/limitations.md](docs/limitations.md)).
- **Known: while a file is rewritten in place, anyone who could read the old file can read the new content,** because its mode, owner and label change only when `cp` ends, and a program that had it open keeps reading it: an existing 0644 file overwritten from a 0600 source is readable by others during the copy. As in 9.84 and plain `cp`; use `-wb` where that matters.
- **Known: a stop during a rewrite costs the old copy:** Ctrl-C, SIGTERM or SIGHUP remove the torn file, SIGKILL or Ctrl-\ can leave it torn; the source is kept, as in 9.84; `-wb` keeps the old copy (see [docs/limitations.md](docs/limitations.md)).
- **Known: a power cut during or soon after a rewrite outside a move can leave the file partial or empty**, as in 9.84; a move fsyncs every landing, and `-wb` each new copy (see [docs/limitations.md](docs/limitations.md)).
- **Known: on a nearly full disk a rewrite can lose the old copy** when another writer takes the room `cp` freed (exit 190, the source kept); the `Space warning` comes first on ext2/3/4, XFS and tmpfs (see [docs/limitations.md](docs/limitations.md)).
- **Known: the beside route never falls back to writing in place:** a rewrite there whose new copy cannot be made, filled, written to disk or renamed keeps the old copy, exit 190 (a 0555 or sticky directory, a bind-mounted file, no room for a second copy, `-co` metadata that cannot be given to a new file) (see [docs/limitations.md](docs/limitations.md)).
- **Known: with `-wb` a rewrite takes its directory's default Lustre or GPFS layout, and none of the old file's `chattr` flags or project id** (see [docs/limitations.md](docs/limitations.md)).
- **Known: off Linux the landing of a rewrite in place can be swapped mid-run, as in 9.84;** use `-wb` there for a root run into a tree others can write (see [docs/limitations.md](docs/limitations.md)).
- **Planned for 9.87:** (9.87: the hang after an early stop and the 3.14 traceback done; see above) what 9.85 planned for 9.86 (the rare hang after an early stop, worker error lines on the progress bar's line, a move's directory fsyncs, macOS `F_FULLFSYNC`, overlapped fsyncs in a move, the 3.14 traceback on an early Ctrl-C, and the rest in the 9.85 section below), the race on a directory on the way, on a first copy's name and on the owner and mode a rerun sets on an identical file, `-enes` counting only what a copy will write, where now a rerun with nothing to copy onto a nearly full destination exits 228, and `cp_supports_sparse` keeping only a real answer, where now a `cp --version` that times out under heavy load sends that worker's rewrites to `cp` by name (see [docs/limitations.md](docs/limitations.md)).

## Upgrading to 9.85 from 9.84

Nothing needs doing to upgrade. What changed:

- **A copy whose two sources landed in one file exits 213:** a destination can take two names for one where no rule on names says so: an 8.3 alias on vfat (`a/longfilename.txt` and `b/LONGFI~1.TXT`), or on a vfat mounted with a codepage `iocharset`, a legacy name that happens to be valid UTF-8 or ASCII. 9.84 checked this only before a move removed a source; a copy without `-rm` exited 0 with one content missing from the destination. After every copy, the move's backstop now looks for landings that are one file with another source's landing and prints `Destination clash: copied SRC, but LANDING is one file with OTHER_LANDING (from OTHER_SRC): the destination took the names for one` for each of the two sources. A source whose landing is not there at all after a copy that reported no error (seen beside an 8.3 alias on vfat) is the same clash: `Destination clash: copied SRC, but it is at none of its landings (LANDING)`. The landing is left as it is: it holds one of the two whole, and the other content has no name of its own there, so rename one of the sources. `-rme` is then skipped, as for any copy error. A move now keeps both such sources, where 9.84 kept only the one whose landing failed its own checks. It costs an `lstat` of each landing, and of a source only next to a link or a shared landing; nothing is read. Memory: 8 bytes for each landing, and 40 more while they are sorted, so a copy's peak is as 9.84's (122 MB for 200,000 files, 373 MB for a million). Time: about 0.3 s per 100,000 files on an idle local disk, and more under load: a cached 100,000-file rerun at load 110 took 1.32-1.73 s with 9.84 and 1.81-2.01 s with 9.85. A file that changed during the copy, or a destination file someone else changed, is not a clash, and the copy still exits 0 for those; a source whose copy failed keeps its own `Copy failed` error; if its landing is also one file with another source's, that is said as `Destination clash: SRC failed to copy, and LANDING is one file with ...`, and the exit is 213.
- **The move's backstop runs in threads only where a stat waits:** chunks of 1,024 entries are looked at in one thread while each takes under 20 us an entry, and in `-j` threads once one takes longer (network storage, a cold disk). On a local disk, 32 threads took 1.2 s per 100,000 files of a move against 0.72 s in one. On NFS mounted `actimeo=0`, 10,000 files took 6.4 s in one thread and 3.0 s in four.
- **A rerun onto vfat no longer copies every file dated before 1980 again:** FAT keeps no earlier time, so such a file's landing never had its time. Where the source is from before 1980-01-01 and its landing at or after it, the skip check reads both files in full instead of copying; for those files only.
- **A link to the destination, named or listed, is the destination:** `printf 'outl\nb\n' | hpcp -sfl - -d out -rme` with `outl -> out` printed "Not removing" for each extra and copied the link in as `out/outl`, a link to its own directory. It is now left out as the destination itself is (`Left out ...: a source that is the destination, or a link to it, is not copied or moved`), asked by what the link leads to (a link into a directory that cannot be searched is copied as a link, as before), with the one `-rme checked nothing` note; the same for `hpcp outl b -d out`.
- **`-rme` asks about extra links once a directory:** an extra symlink is `lstat`ed only in a directory that holds a file or link source, as an extra file already was; on NFS mounted `actimeo=0` that saves about 0.6 ms an extra link.
- **The license is package metadata as an SPDX expression:** the wheel carries `License-Expression: GPL-3.0-or-later` (setuptools 77 and later build it without the "License classifiers are deprecated" warning). pip 9.0.3, the pip of EL7 and EL8, installs and uninstalls it as before (checked on Python 3.6 with pip 9.0.3); it does not read that field, so `pip3 show hpcp` there says `License: None`.
- **Errors the main process prints keep their own lines in a log:** with output redirected, an error printed right after the progress bar was glued to its last line, so `grep '^Destination clash'` missed it; what stdout holds is now written first. Known: an error a worker prints (a `Copy failed` line, for instance) can still follow the progress bar on its line, as in 9.84 (not run; the same count was found on an earlier 9.85 commit), so `grep -c '^Copy failed'` can count fewer than the errors (12 files that cannot be read gave 9 to 11 matching lines in 6 runs, 3 on Python 3.14 and 3 on 3.6); `grep 'Copy failed'` finds them all. Planned for 9.87 (see [docs/limitations.md](docs/limitations.md)).
- **A rewrite goes beside the old file and is renamed over it:** (9.86: only with `-wb`, and by default for a file with other names, one that cannot be opened for writing, or what is not a file; see above) a file that is already at the destination is copied to a hidden `.hpcp_tmp_` name in its directory and renamed over it once whole, so a source that fails on read (a bad sector, an NFS soft timeout: checked with a real EIO on EL7), a full disk or a stop leave the old copy as it was, exit 190. 9.84 truncated the old copy first and lost it. A first copy writes straight to its name, as before, and costs nothing more; a rewrite costs a new file and a rename where 9.84 truncated in place. Each new copy is written to disk (fsync) before it is renamed over the old one, so after a power cut the landing holds the old copy or the new one, never an empty file (on this route: the in-place routes below, and `-co`'s known limitation, write over the old copy, and a power cut during that write can leave the file partial); an fsync the filesystem fails is a `Copy failed` (190) with the old copy kept, and a filesystem that cannot fsync at all (some FUSE ones: EINVAL, ENOTSUP, ENOSYS) is written as before. Measured against 9.84 (1,000 4 KiB rewrites on an idle EL7 VM, three runs each): ext4 4.75 to 5.05 s against 5.84 to 6.58 s, XFS 4.52 to 4.74 s against 5.31 to 6.03 s, about 1 to 1.5 ms more per file, nearly all of it the fsync (without it the rename alone cost about 0.1 ms); on a heavily loaded host (XFS on NVMe, 3,000 rewrites, 8 workers, median of six) 3.7 s against 9.1 s, of which the fsync 2.6 s; over NFS loopback mounted `actimeo=0` from a `sync` export 18.6 to 20.6 s against 21.8 to 23.0 s, the fsync adding nothing (the server commits each write already), the create and rename the rest. A first copy writes straight to its name and is not fsynced (outside a move, below): nothing was there to keep. What a new inode changes: a process holding the old file keeps reading it; an NFS client holding it open may get `ESTALE`, and where the copying client holds it open itself, its NFS client keeps the old one as `.nfsXXXX` until it is closed, which `-rme` then sees as an extra; inotify watchers see the name replaced (moved to), not written; settings a filesystem keeps on the inode and not in a portable xattr are not carried (a Lustre or GPFS layout set with `lfs setstripe` on the file, `chattr` flags such as `+C`, a project id: the new file takes its directory's); and a rewrite costs that fsync, as above. A stale `user.*` xattr or ACL of the old copy no longer survives a rewrite.
- **Written in place only when the source has just read whole:** (9.86: gone; a rewrite goes in place by default, and the beside route never falls back; see above) where a new name cannot be made or renamed (a 0555 directory with a writable file, a sticky directory, a bind-mounted file), a regular file with one name is written in place, as 9.84 did, once the source has been read to its end, and only when the old copy is at least the source's size (written over it, below) or the free space holds the source. Otherwise the old copy stays, exit 190 (`Copy failed: cannot copy SRC to DEST, leaving DEST as it is: WHY`). This includes a rewrite that grows a file on a nearly full disk whose new name ran out of room: 9.84 grew it in place, when the growth fitted. A write in place is not atomic and is not fsynced (outside a move, below): a power cut during it can leave the file partial, as in 9.84.
- **A rewrite in place writes over the old copy:** (9.86: gone; `cp` writes the file, as in 9.84; see above) a file of the same size or smaller that is written in place (the fallback above) is now written over the old copy and then cut to its length. 9.84 had `cp` truncate it first, which freed its room: on a nearly full disk another writer (in 9.85, another worker's temporary file beside its own landing) could take that room, the write ran short, and the old copy was lost (exit 190). Only the source's data is written; where the source has a hole, the old copy's data there is punched to a hole, so the result is as sparse as the source, as `cp` makes it (where the filesystem cannot punch, zeros are written over that data instead). Over a dense old copy the rewrite needs no room on ext4 or XFS. Over a sparse one, the room for the source's data that lands in the old copy's holes is reserved first (`fallocate`, over those holes only), before anything is written: without that room the old copy stays as it was, exit 190 (`... leaving DEST as it is: no room for the source's data where the old copy has holes`), where 9.84 freed the old copy first and could succeed. A reservation that falls short, or is stopped, gives back the room it had taken (the holes are punched again), where the filesystem punches. A sparse old copy on a filesystem that shows no holes (NFS before 4.2) goes to `cp`, as in 9.84, which keeps the holes. On a filesystem that copies on write (btrfs, ZFS, bcachefs), where writing over the old copy needs room for all of it (on a nearly full btrfs that tore the old copy, where `cp` wrote the file whole), the rewrite goes to `cp` as in 9.84, which frees the old copy first (or clones a source on the same filesystem), so there another writer can still take that room and the old copy can still be lost, as in 9.84. An XFS file whose extents a reflink shares also needs room for the overwrite, and on a nearly full disk can still lose the old copy: as in 9.84 with coreutils before 9.0, while with coreutils 9.0 or later and the source on the same filesystem 9.84's `cp` cloned it and needed no room. Both planned for 9.86 (see [docs/limitations.md](docs/limitations.md)).
- **Known: a SIGKILL or Ctrl-\ (SIGQUIT) during a rewrite leaves a hidden `.hpcp_tmp_` file beside the file it was rewriting** (9.86: on the beside route only; see above) (the file itself untouched); `-rme` removes it as an extra (see [docs/limitations.md](docs/limitations.md)).
- **Known: a growing rewrite whose temporary file runs out of room (a full disk, a quota) exits 190 and keeps the old copy** (9.86: on the beside route only, part of "the beside route never falls back"; see above), where 9.84 wrote it in place (see [docs/limitations.md](docs/limitations.md)).
- **Known: with `-co`, a file whose owner, group or an xattr cannot be carried to a new file is written in place after the source reads whole** (9.86: by default `-co` writes a file with one name in place, which keeps all of it; on the beside route such a file keeps its old copy, 190; see above), so a destination failure part way can tear it (see [docs/limitations.md](docs/limitations.md)).
- **Known: a sparse rewrite in place without room for the data that lands in the old copy's holes exits 190 and keeps the old copy** (9.86: gone with the write-over; see above), where 9.84 freed it first and sometimes finished, sometimes lost it (see [docs/limitations.md](docs/limitations.md)).
- **Known: on Windows nothing is fsynced**, as in 9.84 (see [docs/limitations.md](docs/limitations.md)).
- **Known: a move's links made in another user's directory the runner may not read are not fsynced** (see [docs/limitations.md](docs/limitations.md)).
- **Planned for 9.86: an option to write in place instead of beside** (9.86: done the other way round: in place is the default, and `-wb` writes beside; see above), for a per-file Lustre or GPFS layout and readers on other NFS clients (see [docs/limitations.md](docs/limitations.md)).
- **Planned for 9.87: on Python 3.6 and 3.14, a run stopped early (Ctrl-C, SIGTERM) or whose copy worker dies can rarely hang** (9.87: done, the dropped stop and the 3.14 traceback too; see above) (9 in 3300 probe runs, about 1 in 75 early Ctrl-Cs on EL8, about as often as 9.84); a second Ctrl-C does nothing then, Ctrl-\ or `kill -9` ends it (leaving a `.hpcp_tmp_` file where a rewrite was under way, as SIGKILL does), and nothing is removed. Also planned: a stop whose `KeyboardInterrupt` Python drops in the parent (rare) is not acted on there: during the copy it ends with exit 191 (`BrokenProcessPool`) instead of 130 (seen on 3.14), and outside a pool the run goes on to its end; and on 3.14 about one early Ctrl-C in three prints a traceback (see [docs/limitations.md](docs/limitations.md)).
- **A move writes each copy to disk before a source goes:** the worker that copies a file fsyncs the landing before it reports the file copied (a landing an earlier run left, the same size and time, is fsynced too), so a power cut after the move cannot lose both the copy, still in memory, and the source, whose removal was already on disk. 9.84 removed sources with the copies unsynced. A landing the filesystem fails to write is a failed copy: its own error line (`Copy failed: ERROR copying SRC to DEST, ...: DEST cannot be written to disk (Input/output error)`), the landing is removed so that a rerun writes it again, and the move's `Remove skipped: ... the copy reported N error(s)` follows, so no source is removed (checked on EL7 and EL8 with a thin volume out of space, XFS and ext4: 150 MiB moved onto 64 MiB of real space kept its source). Why an fsync of each copy, and not one syncfs(2) of each destination filesystem at the end (what the first build did): before Linux 5.8 syncfs reports no write error at all (EL7 runs 3.10 and EL8 4.18: on that thin volume syncfs returned 0 where an fsync of the same file returned EIO, and the move removed its source); a writeback error is kept only on the in-memory inode, and in a long move the kernel writes early landings back on its own long before any check at the end, an inode evicted under the copy's own memory pressure taking its error with it, whereas an fsync right after the copy, while the data is still dirty and the worker's own descriptor holds the inode, cannot miss it (the loss was reproduced on EL8, kernel 4.18, XFS and ext4: after a writeback error and `drop_caches`, a fresh open's fsync returned OK on a copy that did not match its source; on EL7, kernel 3.10, the error survived `drop_caches` in that setup, so there it was not shown, and the design does not depend on it); and the destination root's filesystem is not every filesystem the copies land on (a mount below it). On ext4 and XFS the fsync of a new file also commits the transaction that made its name and every earlier one (the directories made for it), so no directory is fsynced (ext4: `jbd2_complete_transaction` up to the inode's `i_sync_tid`; XFS: a log force up to the latest LSN that touched the inode; `fsync(2)` itself promises the name only with a directory fsync, so other filesystems may differ). It works wherever `os.fsync` does, off Linux too (not on Windows, where nothing is fsynced). On macOS `fsync` returns once the data is in the drive's own write cache, and only `fcntl(F_FULLFSYNC)` flushes that, so a move there can still lose both copy and source to a power cut: planned for 9.87 (see [docs/limitations.md](docs/limitations.md)); this is from reading Apple's documentation, not a run (there is no Mac here). On Lustre an fsync is sent on as an OST sync: from reading the Lustre client's code, not a run. A filesystem that cannot fsync at all (some FUSE ones: EINVAL, ENOTSUP, ENOSYS) is written as before. A file whose mode lets its owner neither read nor write it (a copy of another user's file of mode 0044, owned by the non-root runner) is given owner read for the open and its exact mode put back through the descriptor at once. Each directory a move makes a link in is fsynced too, once all its links are made (a link has no data to fsync, and links are made after every file; on ext4 and XFS that fsync also commits the directories made before it); another user's directory the runner may not read is passed over. That costs nothing that showed: 20 directories, each holding one file and 100 links to it (2,000 links) moved in 0.57 to 0.77 s on EL7 ext4 against 0.58 to 0.74 s without it, 0.69 to 0.87 s on EL7 XFS against 0.63 to 0.81 s, 0.61 to 0.72 s on EL8 ext4 against 0.59 to 0.69 s, and 0.57 to 0.76 s on EL8 XFS against 0.67 to 0.78 s (3 runs each, interleaved; the hosts were busy, so only the comparison holds). Not fsynced yet (planned for 9.87, see [docs/limitations.md](docs/limitations.md); 9.87: done, see above): a move's empty directories, and a directory's mode, owner or times, where no file or link lands on that filesystem after the directory is made; after a power cut within the journal interval, a moved empty directory, or such a directory's mode, owner or times, can be missing at the destination while the source is already gone. Not fsynced: a block device named by `-d`, onto which a move writes and then keeps every source (213: the device is another kind of entry than the file). A `-di` image is covered: the fsync of a file in the mounted image is flushed down to the image file by the loop driver. What it costs, against the same code without the sync (an fsync of each file is a wait for the disk; the worker count does not hide it where the disk is slow): on an idle EL7 VM (2 vCPUs), 10,000 4 KiB files moved took 79 to 92 s on ext4 against 47 to 54 s, and 72 to 82 s on XFS against 43 to 47 s (1.6 to 1.9 times, about 3 ms a file); beside a 3 GiB writer 86 to 110 s against 48 to 63 s (ext4) and 92 to 101 s against 51 to 56 s (XFS); 4 files of 256 MiB came out alike (1.1 to 3.6 s against 1.3 to 4.9 s, writer or not); on a host's XFS on NVMe (Docker) 4.5 to 5.4 s against 4.3 to 4.8 s quiet and 7.3 to 13.1 s against 4.7 to 8.6 s beside the writer. A move with many small files onto a slow disk takes longer for its safety, and a higher `-j` overlaps the fsync waits (planned for 9.87 in the worker itself, see [docs/limitations.md](docs/limitations.md)): the default is one worker per CPU (2 on the EL7 VM, 4 on the EL8 VM), and 2,000 files of 4 KiB moved with the default against `-j 16` took 18.6 to 22.9 s against 10.3 to 11.7 s (EL7 ext4), 17.9 to 21.2 s against 10.1 to 11.7 s (EL7 XFS), 11.9 to 14.0 s against 9.3 to 11.8 s (EL8 ext4) and 14.2 to 15.8 s against 8.2 to 10.5 s (EL8 XFS), 3 runs each. That the gain is overlapped waits, and not CPU, is an inference (the VMs have 2 and 4 vCPUs, far fewer than 16 workers).
- **What is at a landing is never opened or written through:** a FIFO, socket, device node or symlink below a destination is replaced by the file the source has there: 9.84 hung on a lone FIFO, wrote the file into the disk behind a device node (checked on EL7), and wrote through a link. One that cannot be replaced (its directory refuses) is a 213 that names the directory and the fix, never written through (9.86: on Linux the file a rewrite writes in place cannot be swapped during the run either; a directory on the way still can, deferred). A FIFO or device named by `-d` is still written through, as `cp` writes it (a pipe feed, an image written to a disk), and a link named by `-d` is followed.
- **A symlink inside a destination is replaced by what the source has there (a file or a directory), with a note naming it; name it with `-d` to write through it:** `out/d -> ../elsewhere` becomes a directory `out/d`, and nothing is written to `../elsewhere` or changes its mode (`Note: out/d was a link to ../elsewhere and is now a directory; nothing was written to ../elsewhere. To write through a link, name it as the destination: hpcp src/d/ -d out/d/`). 9.80 to 9.84 wrote src/d's files into elsewhere, and a user who could write the destination could steer a root restore into `/etc`. A symlinked data directory that a rerun wrote through now gets a real directory, on the destination's own disk. Under `-ncd` such a link is not replaced: a 213 for each file below it, naming the `-d` form. A link that cannot be removed (its directory refuses) is a 213 for each file below it.
- **No more refusals for a destination directory that cannot be listed:** 9.81 to 9.84 read each landing directory for links before the copy, on one worker, and refused (213, `chmod u+rx`) a directory it could not read; nothing below a destination is followed now, so nothing can hide there, and `chmod 000 out` takes the copy again, as it did in 9.80. A landing through a link to a source is no longer refused either: the link is replaced.
- **`-co` keeps what was there on a new file:** (9.86: on the beside route only; by default `-co` writes in place, which keeps all of it; see above) the rewrite goes beside too, and the new file gets the old one's owner, group, mode, `user.*` xattrs, POSIX ACLs, SELinux label and FAT attribute bits; a group or a directory's default ACL the new file would take is not kept. As a write in place does, it drops a file capability (`security.capability`), and for a non-root owner set-user-ID, and set-group-ID with group-execute. Where those cannot be carried (another user's file, a group the runner cannot give, an xattr hpcp cannot carry such as `trusted.*`) a file with one name is written in place as 9.84 did, after the source has read whole; one with other names still gets a new file, which the runner owns, so the other names keep the old content. Otherwise the inode changes, as above.
- **A block device named by `-d` that is in use is refused (exit 213):** `hpcp img -d /dev/sdb1` with sdb1 mounted, used as swap, or held by device-mapper, md or LVM says `is in use` and writes nothing: hpcp first opens it `O_EXCL`, which Linux refuses then (a mounted loop device checked on EL7), and holds it until `cp` is done, so no mount can start meanwhile. A plain open by another program (a `dd` writing it) is not seen. 9.84 wrote over it, as `cp` does.
- **SIGTERM and SIGHUP clean up as Ctrl-C does, then end by that signal:** in the main process and in every worker, a stop stops `cp`, removes the temporary file and, for an image, its mounts and loop devices; the run then ends by the same signal, so `timeout`, a shell and systemd see what they sent (Ctrl-C keeps exit 130). A signal the run was started ignoring stays ignored: `nohup hpcp ... &` keeps going on a hangup. A worker whose main process dies (SIGKILL) stops its `cp` and cleans up within about 4 s, under Python 3.14's forkserver too. hpcp uses SIGUSR2 for this; a SIGUSR2 sent to a worker stops it. Only SIGKILL of a worker, or of a serial run, can leave a `.hpcp_tmp_` file.
- **A FIFO, socket or device named as a source is copied, exit 0:** `hpcp a/p -d out/` made the node and exited 200 (`Source path type error`), and `-rf` kept every source (212); it is copied as `cp -a` copies it, and moved with `-rf`. One met in a directory tree is still skipped with a note. A list made by `find` therefore copies its FIFOs and sockets, where the same tree named as a directory skips them.
- **A move of a link and a path through it moves both:** `printf 'lb/\n' | hpcp -sfl - lb/x -d out/ -rf` and `hpcp lb lb/d/ -d out/ -rf`, with `lb -> b`, exited 192 at random and never removed `b/x` (`b/d`); exit 0 now, and the named paths go. A path listed through a link that another source of the run copies as a link (`hpcp lb -sfl list` with `lb/x` in the list) is a 213 for that path, the link copied.
- **A copy into its own inside under another spelling (FUSE exFAT):** `hpcp D/ -d d/sub/` there added a nested copy on every run; the destination is now left out of the walk, as for one spelling, and a pair the directory cannot be asked about is refused (241).
- **A pair of names that fold alike near PATH_MAX is copied:** the probe makes its names relative to directory descriptors, so a landing within about 57 characters of the path limit is no longer a false 213 (`File name too long`).
- **The check before a copy costs the garbage collector nothing per entry:** about 1 to 2 s less per million entries of a list.
- **Known, for 9.87: hints with a name the locale cannot show cannot be pasted into a shell:** with any non-ASCII name under LANG unset, or a non-UTF-8 one under a UTF-8 locale, the replaced-link Note and the `-ncd` hint print the name with Python's escapes (`d\udcc3\udca9`), not shell-quoted (deferred, see [docs/limitations.md](docs/limitations.md)).
- **Known, for 9.87: with LANG unset, a `-siff` apply stops at the first non-ASCII name:** under Python 3.6 on EL7 with no locale (cron, some ssh sessions), the patch apply reads its lists' names as UTF-8 and stops with a UnicodeEncodeError; 9.84 does the same. Run the `-siff` apply with `LANG=en_US.UTF-8` (the locale must be installed: `locale -a` lists `en_US.utf8`); making the patch (`-diff`) and `-dfl` lists are not affected (deferred, see [docs/limitations.md](docs/limitations.md)).

## Upgrading to 9.84 from 9.83

Nothing needs doing to upgrade. What changed:

- **A move keeps a source that its landing does not hold (exit 213):** before a move removes a source file or link, one of its landings must hold it: there, of its kind (a symlink at a file's landing counts as what it leads to, since the copy writes through it; since 9.85 only a symlink named with `-d`, as one below a destination is replaced), of its size and, unless `-co`, of its modification time or else of its contents; not the source itself; and not one file with another source's landing, unless that file has other names (a destination deduplicated by hard links: the copy never writes such a file, it replaces it). A list that names the destination itself (`printf 'out\nb\n' | hpcp -sfl - -d out -rme`) now checks nothing, with `-rme checked nothing`, as the same sources given as arguments always did; 9.83 removed the extras below `out/b`. - **`-co` never reads a FIFO, socket or device node:** a source that is not a regular file is made as `cp -a` makes it, with its mode, owner and times, and never opened. 9.81 read a device to its end and wrote it through what was at the destination, another disk if a device node was there, and a FIFO source hung on the first run. As in a plain run, a user who may not make device nodes gets an error for a device source (9.81 under `-co` got an ordinary file with its contents). The old file at the destination now stays: `cp -a` takes the name away before its `mknod` fails, so a plain run deleted it (9.81 under `-co` emptied it). hpcp asks first, by making a node of that kind beside the destination under a name of its own and removing it, and copies nothing when the system refuses.
- **A device named by `-d` is never replaced (exit 213):** a source that would take the name of a device node that `-d` names itself (`hpcp /dev/sda -d /dev/sdb`, `hpcp a/fifo -d /dev/sdb`, with or without `-co`; a regular file too when the node has other names) is a clash: the node stays, and the message says what fixes it (`-dd` clones a disk; remove the node to replace it). A plain run replaced the node. A link to a disk (`/dev/disk/by-id/...`, `/dev/mapper/...`) is the disk, and is kept as well. The check is per destination: with several `-d` (spill-over, each file lands on one) the file lands on the others with a note, and the run ends as any other run of that source (a move completes); it is a clash, exit 213, and nothing is copied only when no destination is left. A landing on a name that any `-d` gives counts (`-d out/ -d out/n`), not only the name a `-d` spells out. A node for the same device as the source (the pair a first run made, or the same device under another name) is no clash. A symlink source runs no `cp` and keeps its 9.81 result (exit 162, the node untouched). A device node inside a destination directory is a file of the tree, and a node source replaces it. A regular file still writes through a device node, as in 9.81 (see [docs/limitations.md](docs/limitations.md)).
- **xxhash is no longer installed on Python 3.6:** `pip3 install hpcp` on stock EL7 and EL8 failed without a compiler, because pip 9 takes no xxhash wheel and hpcp required it. It now installs there and hashes with blake2b; an xxhash already installed is still used. To add it, upgrade pip first (`pip3 install -U pip`, then `pip3 install xxhash`): on stock pip 9.0.3 `pip3 install xxhash` fails on EL7 and EL8.
- **multiCMD:** the embedded multiCMD is 1.57. It runs whenever the installed one is older, so nothing needs upgrading. With multiCMD 1.57 or earlier installed, pip 9 (stock on EL7 and EL8) without `--user` stops `pip3 install -U hpcp` with `configparser.DuplicateOptionError` once a newer multiCMD is out, because it upgrades dependencies too: use `pip3 install hpcp==9.82`, `pip3 install -U --no-deps hpcp`, or run `pip3 install -U pip` once. With `--user` it does not stop.

## Upgrading to 9.81 from 9.80

- **Lists keep their tree (layout change):** a path from a list (`-sfl FILE`, `-sfl -`, or stdin when no source is given) now lands at `<dest>/<path as given>`, normalised, without a leading `/`, `./` or any `..`, as `rsync --files-from` and `cp --parents` do. 9.80 put every entry flat in the destination, so `src/a/x.txt` and `src/b/x.txt` overwrote each other. Scripts that rely on the flat layout have to change: `cd` into the directory that holds the files, or pass the paths as arguments, which keep their layout. See [Copying from a list](#copying-from-a-list).
- **Same-name clashes are errors (exit 213):** when a file named directly (an argument: `hpcp a/x b/x -d out`, or a list entry) and another source land on one destination file, nothing is overwritten silently any more. The first in order stays, the rest of the run is copied, the clash is named, and hpcp exits 213, as `cp` refuses such a copy. It counts even when the contents are the same. A file named directly against a file from a directory is a clash too. A move (`-rm`) or `-rme` that meets a clash removes nothing.
- **A file against a directory is a clash too (exit 213), in 9.80 as well:** when a file lands where a directory is (one already in the destination, one that another source makes, or one a listed path implies: `d/x` with `d/x/y`), the directory stays, the file is not copied and its source is not removed, and the rest of the run is copied. 9.80 put the file inside the directory (`out/x/x`), and `hpcp a/ -d out -rme -rf` then removed it as extra and removed the source. A directory onto a file (or onto a link to one) leaves that file as it is, with its mode and owner, and is reported the same way (9.80 changed the file's mode, and as root its owner, then failed with exit 193). A symlink source that is a directory is as before. A symlink onto a directory that is not its own name, named directly, lands inside it like a file (`hpcp lf d` gives `d/lf`, exit 0; 9.80 exited 162), and that changes two old results: `hpcp lf -d lnd`, with `lnd` a link to a directory, used to replace the link `lnd` and now gives `d/lf`; `hpcp a/x -d la`, with `la` a link to the file's own directory, used to replace the link and now exits 0 and changes nothing. A link to a directory given with `-rme` is still refused (exit 212). A file named directly onto an existing directory still lands inside it (`hpcp a/x d` gives `d/x`, in every mode, as in 9.80); only a `d/x` that is itself a directory is the clash.
- **A file that would land on a source file is refused (exit 213), 9.80 as well:** hpcp works out, on real paths and file by file, where each file lands, and refuses the whole run before anything changes when a file would land on a source file (its own too, in a move), unless, in a copy, that file belongs to a directory that lands on itself, which reads and writes nothing. It names both paths. `cp` rewrites a file in place, so another `cp` reading it gets nothing or a part, and a move then removes the path that held the other content: 9.80 could leave an empty file, both contents gone, the sources removed, exit 0. Examples, each with a file at both places: `hpcp p/q/ -d p/` with `p/q/x` and `p/q/q/x` (one source over its own tree), `hpcp d1 d2/d1/ -d d2/`, `hpcp a out/a/s -d out/`, and `printf '../../c/r\nr\n' | hpcp -d .. -rf` run in `w/D/c`. A link changes nothing, and neither does a bind mount of the destination or another case of its name on a casefolded filesystem: `hpcp d1 l2/d1/ -d d2/`, with `l2` a link to `d2`, is the same run, and so is a landing that a link in the destination sends onto a source (`hpcp src/ -d out/` with `out/e -> ../src/d`, or a `cp` that would write through `out/x -> ../a/x`). What runs: a landing on a path where no source has a file, inside a source's tree too (`hpcp p/q/ -d p/` with only `p/q/q/only`); a directory that lands on itself, which another source updates as it would any destination (`hpcp */conf -d merged/`, every run; `hpcp a/ out/sub -d out/`). A file named directly that lands on itself is not given up that way: `hpcp x y/x -d ./` is refused. Only what is really copied counts: a path left out by `-e` and a special file land nowhere. `-do` and `-di` do not look. A move onto itself or into itself, as a whole, is exit 241 as before.
- **A landing in a directory that answers nothing is refused (exit 213), 9.80 ran:** `chmod 000 out; hpcp a/ -d out/ -rf` went on in 9.80, because the run's own directory sync changed `out`'s mode. With neither read nor search permission nothing can say whether a link in `out` sends a file onto a source, and going on lost data, so hpcp names the directory and the fix (`chmod u+rx out`). One permission is enough to answer: a listing (0600) or a question by name for each landing (0300), and those run as they did. A link they find is followed, and a link that leads through a place the run cannot search is refused too. A directory no file lands in stops nothing: a source with a locked subdirectory repeats 9.80's exit on every run.
- **A failed copy leaves the destination's old file, 9.80 deleted it:** when `cp` fails, only what it changed goes, so a source that cannot be opened no longer costs the good copy a backup already holds. A part that `cp` wrote still goes, also after the last retry, where 9.80 left it.
- **A source that holds the destination leaves it out, 9.80 made a copy of it:** `hpcp . -d out/` and `hpcp .. -d out/`, like `find . | hpcp -d out`, now copy everything but `out/` itself, and one line says so. So does a directory named without a slash that is the destination: `hpcp * -d backup/` with `backup` in the working directory leaves `backup` out, on every run. Its files then count as any file of the destination: another source that lands on one overwrites it. 9.80 copied the destination into itself (`out/out/...`, one level deeper each run), reading files that other sources were writing, so such a copy could come out empty or cut short, exit 0. `-rme` then checks nothing and says so: all that is in the destination belongs to that source. Moved, a source that holds the destination is still refused (exit 241); one that is the destination is left out (exit 0).
- **`..` lands in the destination, as `.` does:** `hpcp .. -d out/` put the files in `out/..`, so they went next to `out/` and `out/` stayed empty. A landing never leaves its destination now: the contents of the directory land in `out/`, as with `hpcp . -d out/`, `hpcp ../ -d out/` and `hpcp .. -d out`, which always did that.
- **Overlays still work:** directories that merge (`hpcp base/ overlay/ -d out`) are not a clash: the later source's file wins, exit 0, as in 9.80. The winner is now the same in every mode (9.80's batch copies could race), and one line says how many files a later source replaced. In a move (`-rm`) nothing is removed when a later source replaced a file, since the earlier source holds that file's only copy: the destination has the later files, all sources stay, and hpcp exits 212. A source named twice (`hpcp a/ b/ a/ -d out`) wins its files back, as a sequential copy does.
- **List entries inside the destination are skipped:** an entry whose path lies inside a destination (or is it) is not copied or moved, and counts as any file of the destination: another entry that lands on it overwrites it. One line says how many. `find . -name '*.log' | hpcp -d archive/ -rf` can run every night: the second run no longer moves `archive/app/app.log` into `archive/archive/...`. With no `-d` the destination is the working directory, so `find src | hpcp` skips everything and exits 0. A directory that holds the destination (`cd src && find . | hpcp -d out`) is copied without the destination; moved, it is refused (exit 241), as a move onto itself is. A relative entry is copied, not skipped, only when it and the working directory share a directory strictly inside every destination that holds the entry (by each spelling of its path: as given, and through its links) and its landing is neither the entry nor below it: `cd t/overlay; find etc -type f | hpcp -d ..` lands them at `t/etc/...`. Everything else stays and a second run finds the same: absolute entries, the destination itself and what is directly in it (`cd t/a/b; printf '../../a\n' | hpcp -d ..`), entries that would land on themselves (`-d .`). One case copies once: `find ../../a -type f` from `t/a/b` also lists `t/a/b/g`, which parts from the destination at `b`, so it lands at `t/a/a/b/g`; the second run skips that copy too.
- **Known limitations and deferrals** (see [docs/limitations.md](docs/limitations.md)): a symlink in the destination at a directory's path is written through, with the target's mode and owner changed (deferred in 9.81 and still open in 9.82); with `-nds`, a directory source meeting a file in the destination exits 70 with a `File exists` traceback instead of a clean exit 213, the file untouched (deferred in 9.81, fixed in 9.83); positional `-rme` judges the whole destination, not only where the source lands: `hpcp b -d out/ -rme` also removes `out/keep` (deferred in 9.81 and still open in 9.82; see the `-rme` note below); `-rme` can take a source inside the destination for extra: `hpcp out/sub/ b/ -d out/ -rme`, answered y, deletes `out/sub/x` (deferred in 9.81 and still open in 9.82); a move of a link's directory and a path through the link can end in exit 192, nothing lost (deferred in 9.81 and still open in 9.82); the check before a copy holds a list's jobs in memory and scans existing destination directories one by one (deferred in 9.81 and still open in 9.82); a stored list used under another spelling can match by chance, and then `-fl STORED -rme` offers the other files for deletion (known limitation).
- **`-rme` with a list judges only below its directories; with only named files or links it checks nothing:** with a list, only what the list's directories cover is cleaned; a list of files cleans nothing and says so, and everything else in the destination stays. 9.80 took everything in the destination that was not on the list for extra. To mirror a directory, list the directory itself (`printf 'src\n' | hpcp -d out -rme`): listing only its entries leaves what sits directly in `out/src` alone. Arguments judge the whole destination as soon as one source is a directory: it is checked against everything the sources copy, so `hpcp b -d out/ -rme` with `b` a directory removes `out/keep` (after the prompt), as in 9.80; limiting that to where the source lands is deferred to 9.82 ([docs/limitations.md](docs/limitations.md)). When every source is a named file or a link (`hpcp a/x -d a -rme`, `hpcp lf -d . -rme`), the files are copied, `-rme` says it checked nothing and nothing else is touched (9.80 took the rest of the destination for extra after a prompt, or exited 212). A file with a directory (`hpcp a/x e/ -d d -rme`) or a directory alone cleans as before; `hpcp a/x d/ -rme` no longer cleans `d/`.
- **Prompts with the list on stdin:** when stdin held the list, `-rme`, `-rm` and a move ask on `/dev/tty`, so `find ... | hpcp -d out -rme` works at a terminal. With no terminal they refuse (exit 147), as before. When stdin was not the list nothing changes.
- **List parsing:** lists are read as bytes, so any file name works under any locale. Data with a NUL byte is NUL-separated and exact (`find -print0`, `fd -0`), with no flag. Otherwise lines split on newline only, a trailing CR is dropped, and a line with surrounding whitespace is the exact name when that exists, else the stripped one.
- **Rerunning a FIFO source no longer hangs (9.80 as well):** `hpcp a/p -d out/` or a list holding a FIFO, run a second time, waited forever, because the check for an identical file opened the FIFO. Only regular files are compared by content now; nodes of one kind for the same device (two FIFOs, two `/dev/null`) count as identical without being opened.
- **Dangling symlinks** given as sources are copied as links (`-rm` removes them); 9.80 reported them as not found.
- **`-fl` from a list** stores names with the list's tree. `-fl STORED -rme` with a source from a list deletes nothing: give the source as an argument.
- **`-fl STORED -rme` fixes (9.80 as well):** `-fl STORED -rme` only compares the tree with the stored list and removes extras: it copies nothing and ignores `-d`, in 9.80 too. `hpcp src -fl S` then `hpcp src -fl S -rme` deleted every file in `src`, since the stored lines carry `:digest` (or `:target` for a link) and no name matched. A line now also means the name before each `:` in it, so a name that holds a `:` is kept too. A stored list is never split at NUL bytes (only `-sfl` lists are), a missing one removes nothing (exit 208), one that shares no name with the tree (empty, `/dev/null`, made for `s/` and used for `s`, or the reverse) is nothing known too: it removes nothing, asks nothing, says `Remove skipped` and exits 212, and a name with a line break is never removed: a stored list cannot tell it from two lines.

## Copying from a list

`hpcp` reads source paths from `-sfl FILE`, from `-sfl -`, or from stdin when no source is given and stdin is not a terminal, so it takes the output of `find` or `fd`:

```bash
find src -type f -name '*.log' | hpcp -d out   # out/src/.../x.log
cd src && find . -type f | hpcp -d ../out      # out/.../x.log: cd to leave src out of the destination
find src -type f -print0 | hpcp -d out         # NUL-separated: any file name is safe, no flag needed
fd -0 -e log . src | hpcp -d out
```

- Each path lands at `<dest>/<path as given>`, normalised, without a leading `/`, and `..` never leaves the destination: `../x/a` lands at `<dest>/x/a`. Directories the path implies that this run creates take their sources' mode and owner, so a private one stays private (`-nds` skips that); one that exists already (a directory, a symlink, even a mount point) is left as it is. A directory that is itself on the list copies its metadata onto an existing one.
- A list always means the destination is a directory, even for one entry.
- A directory in a list copies recursively. An entry below a listed directory is already covered, so plain `find src | hpcp -d out` gives one complete tree, with nothing copied twice.
- An entry inside the destination is not copied or moved (see [Upgrading to 9.81](#upgrading-to-981-from-980)); neither is the destination inside a listed directory.
- Arguments keep their own layout (`hpcp src -d out` copies the contents of `src` to `out`). Given both, each source follows its own rule.
- `-rme` with a list cleans only below the directories on the list: `printf 'src\n' | hpcp -d out -rme` mirrors `src` to `out/src/...` and leaves the rest of `out` alone. A directory skipped for lying inside the destination is not one of them. A list naming no directories checks nothing, and says so (so does `hpcp a/x -d out -rme` with only named files or links). It asks first, on `/dev/tty` when stdin holds the list; with no terminal it refuses (exit 147).
- `-nb` with a list starts a worker pool per source, about 23 ms each, so keep the default batching for big lists. See [docs/limitations.md](docs/limitations.md).

## Upgrading to 9.80 from 9.79

- **`<TOOL>_PATH` warnings:** every `<TOOL>_PATH` variable (`CP_PATH`, `MOUNT_PATH`, `DD_PATH`, ...) that does not name an executable is now named once at the start of every run (`Warning: CP_PATH=... is not an executable file; using cp from PATH.`). 9.79 named one only when it started that tool itself, so a bad `CP_PATH` (cp runs in the worker processes) was never named. A tree deeper than the hard limit (`ulimit -Hn`: 524288 on systemd hosts, 4096 on EL7) stops with "Too many open files" errors and leaves its deep part. On macOS the soft limit (256) stays, so trees deeper than about 250 levels stop there. A forced apply already held one descriptor per level in 9.79 and stopped at the soft limit (often 1024), so it now removes deeper trees than before. See [docs/limitations.md](docs/limitations.md).
- **multiCMD 1.56** was required in 9.80 (`pip` installs it). Without it, or with an older one, hpcp used its built-in copy, which was the full multiCMD 1.56; since 9.82 the built-in copy is 1.57 and is used whenever the installed one is older, while pip's floor stays 1.56 (see Upgrading to 9.82).

## Important Implementation Detail

By default, **hpcp** only checks:
1. The file’s relative path/name is identical.
2. The file mtime is identical.
3. The last `-hs --hash_size` bytes (defaults to `65536`) are identical.

Although in most cases these checks should confirm that both files are identical, in certain scenarios (like bit rot), corrupted files might not be detected. If you need to verify file integrity rather than perform a quick sync, it is recommended to use the `-fh --full_hash` option.

A file or directory that cannot be read, listed or written is reported and the rest of the copy goes on; hpcp then exits with a non-zero code (`Copy failed` 190, `Directory sync error` 193, `Source path not found` 207, `Listing error` 209, ...). FIFOs, sockets and device nodes in a tree are not copied: each is noted (`Special file skipped`, no error); one named as a source is copied as `cp -a` copies it.

Nothing below a destination is followed. A file that is already at the destination is written in place: hpcp opens it (never through a link, never waiting on a FIFO) and `cp` writes that open file (on Linux through `/proc/PID/fd/N`; off Linux, or where `cp` cannot reach it, by name, as in 9.84), so its inode stays, with what the filesystem keeps on it. A source that fails part way, a stop or a full disk can then cost the old copy (exit 190, the source kept): `-rbw` reads the source to its end first, and `-wb` keeps the old copy. A file with other names, one that cannot be opened for writing, one to be replaced by a FIFO, socket or device node source (`cp -a` makes those anew), and a FIFO, socket, device node or link below a destination are replaced by a new file written beside them (a hidden `.hpcp_tmp_` name) and renamed over them once whole, never opened or written through; `-wb` does that for every rewrite, and that route never falls back to writing in place (the old copy stays, exit 190). What `-d` names itself is followed and written through, as `cp` does with its destination (a pipe, a disk image, a link). Before a copy that may not fit, on ext2/3/4, XFS and tmpfs, hpcp prints a `Space warning` and then tries, as `cp` does. As with `cp -a`, a non-root copy keeps the group when the user belongs to it but cannot keep another user's ownership, and then does not keep a set-user-ID / set-group-ID bit (on files or directories) for an owner / group it could not keep.

Symlinks are recreated as symlinks, as `cp -a` does: a link whose target is outside the copied tree (say `../shared/lib`) is copied as it is and does not resolve at the destination unless the target is already there. With `-lt --link_tracking`, a relative symlink whose target is missing at the destination gets its target copied to the same relative place, which can be outside the destination directory (and can be a whole tree: `data -> ../../scratch`), so the link resolves there too. `-nlt --no_link_tracking` (the default) overrides `-lt`, and `-lt` does not apply with `-dd` (each partition's links are copied as they are). A new `-di` image is sized for the sources alone, not for what link tracking adds: a tracked tree that does not fit is reported as copy errors. With several destinations a relative link goes to the destination that holds its target. A link whose path is taken by a real file or directory in the destination is not created and is reported.

Setting `-hs --hash_size` to `0` disables hash checks entirely. This can be helpful on HDDs, as they usually have suboptimal seek performance. However, HDDs are also more prone to bit rot. If the operator can accept that risk, it is possible to rely solely on mtime checks for file comparison by setting `hash_size` to `0`. (Though on a single HDD, the standard `cp` command is already well-optimized.)

## Disk Imaging Feature Note

Only available on Linux currently!

`-dd --disk_dump` mode differs from the standard Linux `dd` program. **hpcp** will try to mount the block device/image file to a temporary directory and perform a file-based copy to an identically-created image file specified with `-di --dest_image`. This functionality is implemented crudely and is still an **alpha** feature. It works on basic partition types (it does not work with LVM) with GPT partition tables and has been proven able to clone live running system disks to disk images, which can then be booted without issues. A disk's partitions are the ones whose parent is the disk itself: devices stacked on them (md arrays, LVM, dm-crypt) and the partitions of such devices (a partitioned md array built on the disk) are never taken for the disk's own. A source partition that is not mounted is mounted read-only (an xfs with `nouuid`, so a clone of a disk whose xfs is mounted on this host can be read); the kernel still replays a dirty journal or log when the source device is writable, so the copy is of the recovered filesystem. A partition that is mounted (a live system disk) is mounted the way it is live, read-write when it is, since the kernel refuses a mount that would change that.  
The created disk image can be resized using the `-ddr --dd_resize` option to the desired size. (This feature is provided so that you can shrink the raw size of the resulting image and provides some shrink capability for XFS.)  
For partitions that **hpcp** cannot create a separate unique mount point, **hpcp** will fall back to using the Linux program `dd` to clone the drive. Note that this can be risky and can lead to broken filesystems if the drive is actively being written to. (However, since you generally cannot mount that partition on the current OS, the real-world scenarios for this remain limited.)

### Filesystem parameter mirroring

In `-dd` mode `hpcp` reads each source filesystem's creation parameters and recreates the
destination with matching geometry and features, instead of whatever the local `mkfs` defaults
happen to be. Coverage varies by filesystem: ext2/3/4 (block size, inode size, inode ratio, reserved
percentage, full feature set), xfs (block/sector/inode/directory geometry and v5 feature flags),
btrfs (nodesize, sectorsize, checksum type, features), FAT (width, sector and cluster size, FAT
count, reserved sectors), ntfs and exfat (cluster and sector size), f2fs (geometry and features),
udf and reiserfs (block size and format), hfs+ (allocation block size), and minix (filesystem
version and filename length).

Without it, a clone built on a modern host can be unmountable or unbootable on the system it came
from — for example a FAT32 EFI System Partition recreated as FAT16, or an ext4 `/boot` that gains
`metadata_csum` and `64bit` that its bootloader does not understand.

Size-dependent values are scaled rather than copied, so `-ddr` resizes stay valid: the ext inode
*ratio* and reserved *percentage* are mirrored, never absolute counts. If `mkfs` rejects a mirrored
parameter set, `hpcp` warns and retries with defaults rather than failing the copy. Use `-nfp` to
turn mirroring off entirely.

## Patch Images Feature Note

Only available on Linux (loop devices and mounts, so usually root).

`-diff [PATCH.img]` compares a new tree (a directory, or a single-filesystem image with `-si`) against a base (`-d DIR` or `-di IMG`) and writes a patch image. The patch is an ordinary xfs/ext4 image, split with `-dis` like `-di` output. It holds every added or modified file **whole** at its real path, plus `.hpcp_diff/manifest` and `.hpcp_diff/changes.tsv`, which list every added, modified and deleted path with its before and after state. A moved file appears as one delete plus one add. A file counts as modified when its content, size, mtime, mode, owner, ACLs, file capabilities or user xattrs change; a directory when its mode, owner, ACLs or user xattrs change; a symlink when its target changes. Other xattrs (such as `trusted.*`, `security.selinux` or filesystem-internal ones) are ignored. Without a value the patch is named `DIFF_<src>_TO_<base>_<time>.img`. A file that changes between the comparison and the payload copy (on a live source) stops generation before any manifest is written; exclude it with `-e` or generate from an offline copy. For a directory source, `-e` and `-x` patterns are matched against its real paths, as when copying; for a `-si` image they are matched against `/` plus the path inside the image's filesystem, so `-e '/var/log/*'` leaves out what is under `var/log` there (and `*/tmp/*` only a `tmp/` inside it). Patterns written against hpcp's temporary mount path (for example `/tmp/*/var/log/*`) no longer match; write them as `/…` paths inside the filesystem. A pattern that would exclude the compared tree's root (such as `-e /`) is refused, and blank lines in an `-x` file are ignored. This run's input images (`-si`, `-di`) and the base or new directory are left out of the patch when they lie inside a directory being compared, so `hpcp -diff / -di /root/golden-v1.img` does not install the old image on every node. A payload copy is read again to check it only when its source may have changed since the comparison: on a read-only filesystem (a `-si` image, or a golden mounted read-only) only when the file's stat moved, and on a live one only when the file's inode, size, mtime or change time moved, it was changed shortly before the comparison (within twice the kernel's dirty-page writeback interval, about 70 seconds with default settings, since a write through a memory mapping may leave the change time alone until then; every copy when periodic writeback is off), or it lies on a filesystem whose change time hpcp does not rely on (anything but ext2/3/4, xfs, btrfs and f2fs). With `-fh` (and on FAT, whose files are always hashed in full) every copy is read again, whatever its source, so a copy that came out wrong is caught before the patch exists.

A `-di` image store keeps files at their absolute source path. When the base is such a store, a directory is compared only with its own subtree inside the store, and the patch uses the same layout. So `hpcp -siff patch.img -di store.img` updates the store in place, and `hpcp -siff patch.img -d /` updates the live system.

`-siff PATCH.img` applies a patch to `-d DIR`, `-di IMG` or a single path. Repeat it for every `-dis` volume. It first checks every path the patch touches. If the target differs from what the patch expects, it lists the conflicts and asks `Apply anyway? [y/N]`; the default, and any non-interactive run, aborts. `-fa --force_apply` applies anyway and prints each conflict as a warning. Re-running a patch is safe because already-updated paths are skipped, and every touched path is verified afterwards.

Files and symlinks are replaced atomically: the new version is written next to the old one, written to disk (an fsync, one file at a time as each is renamed) and renamed over it, so running processes keep the old file and an interrupted apply leaves each file either old or new. The fsync costs about 1 to 3 ms a file (5,000 rewritten files, 2 workers, idle EL7 VM: ext4 23 to 24 s without, 26 to 31 s with; XFS 26 s against 35 to 39 s); it is taken one file at a time in the parent's loop, because fsyncing in the workers measured slower there (ext4 38 to 53 s, XFS 41 to 44 s). A directory the patch deletes is removed only if it is empty once the patch's own deletions are done; whole trees are removed only for conflicts forced with `-fa`, and that removal never enters a mounted filesystem (bind mounts included): a directory holding a mount point is left in place with the mount, that row fails verify, and a note names the mount before the prompt. Paths are followed through symlinked directories that stay inside the target; if any path the patch deletes or writes resolves outside the target through a symlink, nothing is applied, even with `-fa`.

A single-filesystem patch pairs names by exact case, so a case-only rename (`EFI/BOOT` to `EFI/Boot`) is a delete plus an add, and the target ends with the new spelling. Rows are planned per filesystem: the target's own and each one mounted below it (for example the ESP at `/boot/efi` when applying to `/`). An automount (direct map) the patch writes into (an ESP that systemd mounts on demand, shown as autofs until something enters it) is mounted first, so it is planned as what it holds; one that cannot be mounted stops the apply before anything changes, and so does an indirect automount map (only its keys mount; leave it out of the patch with `-e`). A file written by one filesystem's rows and then removed, through a symlinked directory, by a later filesystem's delete is reported by verify (failed), not written again; and an entry replaced twice by contradictory rows of one patch can in principle reuse an inode number, which verify then cannot tell apart (both need patches that contradict themselves). On FAT, exFAT and HFS/HFS+ (not case-sensitive HFSX) names are matched case-insensitively, so such a rename applies, with or without a content change, and a re-run skips it. On FAT, exFAT and NTFS rows are compared and written by content only, since modes and owners there come from mount options. On FAT, which stores local times, a file whose mtime differs only by a timezone offset (a whole number of 15 minutes, at most 24 hours) with the same content counts as unchanged; files on FAT on either side when the patch is made (including a mount below the source root, such as `/boot/efi`) are hashed in full for this, whatever `-hs` says (a golden whose ESP was a plain directory is hashed by its tail, so there the tolerance covers files up to the `-hs` size only). Such a patch (for example a `-diff` of `/` with a FAT ESP mounted below it) is format version 3, which hpcp 9.68 and older refuse. A replaced FAT file keeps its read-only, hidden and system attributes. A write that lands on an entry another row found already done (through a symlinked directory, or a name differing only by case) is reported by verify. The filesystems are applied in turn, the target's own first; if one fails, the ones after it are not applied. When a delete removes an entry whose add or update was skipped as already done (a case-insensitive filesystem hpcp does not recognise, or a symlinked directory alias), the apply writes it again and counts it as `restored`.

An apply that is killed partway leaves directories it created private (mode 0700, owned by root) until the final metadata pass runs. Re-running the same patch then reports those directories as conflicts; re-run with `-fa` to finish.

`changes.tsv` is also what `-dfl` writes:

```
#hpcp-changes	1
#op	path	old	new
D	gone.txt	f:<size>:<mtime_ns>:<mode>:<uid>:<gid>:<hash>:<xattr>	-
A	newdir/	-	d:<mode>:<uid>:<gid>:<xattr>
M	link	l:old-target	l:new-target
```

Paths escape `\`, tab, newline and carriage return as `\\`, `\t`, `\n`, `\r`.

Limitations:

- Hard links are not preserved; applying a patch breaks them.
- Special files (FIFOs, sockets, devices) are ignored.
- Even a small patch is an image of roughly 50 MiB.
- Generating and applying a patch need root (loop devices, mkfs, mount).
- Nothing else may modify the target while a patch is applied.

### Disk patches (`-dd`)

`hpcp -dd -diff [PATCH.img] NEW_DISK -d OLD_DISK` patches whole GPT disks — for rolling a new golden image out to nodes cloned from the previous one. Both disks are block devices or disk-image files and are only read; MBR (msdos) disks are refused. The patch holds one section per filesystem partition (the same change list and payload as a single-filesystem patch), raw copies of areas that cannot be patched file by file when they changed (BIOS-boot and unknown-filesystem partitions, the MBR boot code), and the identity values that changed (filesystem UUID / label, GPT partition GUID / name / attributes, disk GUID). Swap contents are never carried. `-e` patterns are matched against `/` plus the path inside each partition's filesystem: `-e '/var/log/*'` leaves out what is under `var/log` on the root partition and `-e '/EFI/Linux/*'` what is under that directory on the ESP (a separate `/var` partition holds `log/` at its root, so there the pattern is `/log/*`); `*/…` patterns apply on every partition. This run's temporary directories and its disk-image files are left out wherever a live mount of a partition shows them: the whole filesystem, a btrfs subvolume mounted as the root (Fedora's `root`), or a bound directory.

`hpcp -siff PATCH.img -d TARGET_DISK` applies it to a node disk — a block device (a symlink such as `/dev/disk/by-id/...` is fine) or a disk-image file — offline or live:

- The target must have the base's layout: the same partition numbers, type GUIDs and filesystem types (sizes may differ, except raw areas). Layout changes need a re-clone.
- On a live disk, mounted partitions are patched through their live mount. Raw writes and identity changes to a partition that is mounted, active swap or held by LVM/md are refused before anything changes — apply such patches offline. An in-use raw area is not read, so it is refused even if it already holds the new content; an offline apply skips it then.
- FAT, exFAT and NTFS sections (the ESP) are compared and applied by content only: their permissions and owners come from mount options, so differences there are ignored. On FAT sections, files are hashed in full and a file whose mtime differs only by a timezone offset (a whole number of 15 minutes, at most 24 hours) with the same content counts as unchanged, since FAT stores local times (exFAT and NTFS record UTC times and get no such tolerance). A replaced FAT file keeps its read-only, hidden and system attributes. Names are generated by exact case, so a case-only rename (`EFI/BOOT` to `EFI/Boot`) is carried and the node ends with the golden's spelling; FAT, exFAT and HFS/HFS+ sections match names case-insensitively when applying (case-sensitive HFSX is detected). HFS and HFS+ sections compare owners and modes too (hfsplus keeps them on disk).
- Filesystem sections are applied first (ESP last), then raw areas, the MBR boot code, and identity changes; everything is verified afterwards. A section that fails stops the apply before any later section, raw area, boot code or identity change (so does a failed restore or final verify across sections), and a raw area that cannot be written, or that does not hold the new content when read back right after its write, stops it before any later raw area, the boot code and identity changes (boot code that does so stops the identity changes): fix the cause and re-run, and the re-run skips what is already done. Apply prints one line per section and a total.
- Every partition the patch carries a raw area for (even one already done) or whose UUID or label it sets must open exclusively (`O_EXCL`) before anything changes; one that is mounted, active swap or held by LVM/md/dm — in this or another mount namespace — is refused (`Disk in use`). During the raw writes and identity changes hpcp locks the whole disk (`flock`, so udev leaves it alone) and holds those partitions exclusively; raw areas are read back past the page cache.
- A node's filesystem UUID or label that differs from the golden base is warned about and replaced only when the patch changes that value; otherwise the node keeps its own.
- Filesystem labels, GPT partition names and exFAT serials are read and written exactly: non-ASCII characters, spaces, `=` and apostrophes included (GPT names keep leading and trailing spaces too; libblkid drops a filesystem label's trailing spaces, except on btrfs and NTFS, whose labels come from their own tools); `-dd` copies keep them the same way. Disk patches made by hpcp 9.67–9.69 for disks with such labels or names recorded them mangled or cut short, so regenerate those patches.
- Every refusal that needs no hash (a partition in use, an identity change that cannot be made, a missing raw payload, a section that cannot be mounted) comes before any raw area is read, and so does, when generating, a size change of a partition that is raw by its type (one that falls back to raw because it cannot be mounted is checked once that is found); a raw area too large for `-dis` is refused right after the raw areas are hashed when they alone force more than one volume (otherwise once the filesystems' payload is known).
- An image file that is already attached to a loop device is refused (`Disk in use`); apply to that loop device or detach it first.
- A patch whose FAT files carry full-hash marks is written as format version 3 (patches made with `-fh` or `-hs 0` carry none); hpcp 9.68 and older refuse it ("newer than supported"). Patches without them keep format 1 or 2.

## Several Destinations

Several `-d` are spill-over, not copies: each file goes to one destination, the first with room (`-rds`: a random one), and an identical file at any destination is skipped. A file there that differs, even only in its mtime after a plain `cp`, is not skipped, and a different file at a later destination stays as a second version.

## Remove Extra Feature Note

`-rme --remove_extra`: Especially when combined with `-rf`, **PLEASE PAY CLOSE ATTENTION TO YOUR TARGET DIRECTORY!**  
`--remove_extra` removes the files that the sources do not copy, below where each directory source lands: all of the destination for `src/` (it lands in `out/` itself), only `out/b` for `b`, and what a list's directories cover for a list (see [Copying from a list](#copying-from-a-list)). A named file or a link judges nothing, so when every source is one (`hpcp a/x -d out/ -rme`), or a source is or holds the destination (`hpcp . -d out/ -rme`), it checks nothing, says so, and removes nothing. Check what is in a mirrored destination before you confirm. Nothing that is a source, lies in one, or holds one is removed, whatever the destination calls it: a source inside the destination (`hpcp out/sub/ b/ -d out/ -rme` keeps `out/sub/x`) stays, with a note. A link is judged as a link, not by where it leads: `out/d -> ../src/d` is an extra like any other, and goes.

It runs only after a copy that reported no errors: if a source path could not be listed, its copy in the destination would look extra. Otherwise hpcp leaves the destination as it is and exits with `Remove skipped` (212). With `-di` the image holds each source at its absolute path, and `-rme` compares against that layout: it mirrors the **whole image** to this run's sources, so another source copied into the same image on an earlier run is removed too. The destination's copy of an excluded path (`-e`, `-x`, absolute or not, a link's excluded target included) is never removed, and a directory that still holds one is kept. With `-lt`, link targets that link tracking placed in the destination are kept too; without it they are not part of the copy and are removed like any other extra file, unless excluded. A filesystem mounted below the destination (a mount or a bind mount, or another device such as a btrfs subvolume, as with `rsync -x`) is left alone with everything in it: its files are not listed as extra and its directories are not removed. That includes one mounted only when its directory is entered (an automount, an NFSv4 submount): each directory is checked once open, before anything in it is read. A destination, or a moved source, that is itself such a mount is taken as mounted. The destination's own filesystem is cleaned even when the destination is a mount point itself (a `-di` image, a disk). A filesystem's own `lost+found` (directly at its root, as in a `-di` image or an ext4 destination) and what fsck put in it are never removed.

## Remove Feature Note

`-rm --remove` can remove files in bulk. This might be helpful on distributed file systems like Lustre: without a destination it walks each tree once, by directory descriptors (one open and one listing per directory, no stat per file), and with `-pfl` empties the directories in parallel jobs; `-rwloff` lists the trees first and then removes the listed files in parallel jobs. Every removal (plain `-rm`, a move, `-rme`) goes by directory descriptors from each source or destination, recorded before the confirmation prompt, without following symlinks: a source or destination replaced, or a directory in it swapped for a symlink, while hpcp runs (a tree other users can write to, with hpcp running as root) is not removed through, and is reported. Excluded paths stay, with the directories that hold them. As with `rm --preserve-root`, `hpcp -rm /` (or a bind mount of `/`) is refused (`Invalid arguments`, 241).

A removal (a forced patch apply, `-siff` with `-fa`, too) holds one directory descriptor per level of the tree, so a tree deeper than the open-files limit stops with "Too many open files" errors and leaves its deep part; see [docs/limitations.md](docs/limitations.md).

With a destination, `-rm` copies first and then removes the sources: a move. A move that lands a source on itself (`hpcp -rm /data/x -d /data/`, `hpcp -rm a/ b/ -d a/`) or whose destination lies inside it is refused before anything is copied (`Invalid arguments`, 241). A directory named without a slash that is itself the destination is left out, and the rest moves: `hpcp a b -d b/ -rf` moves `a` into `b/`, leaves `b` and exits 0. The sources are removed only if the copy reported no errors (a source named as an argument that is not there, a file that failed to copy, an unreadable directory, a path longer than 4096 characters, a link that could not be created); otherwise they are left in place and hpcp exits with `Remove skipped` (212). A move removes only the files and links the copy listed, then each source directory that is empty after that. Anything else stays where it is, with the directories that hold it: a file written to a source after the copy listed its directory, a special file (a FIFO, socket or device node, which hpcp does not copy), an excluded path. What stays, excluded paths aside, is named in a `Move left entries` note (exit code 0). A file changed after it was copied is still removed, as with `mv`, so stop writing to a source before moving it. The removal goes by directory descriptors from each source root, without following symlinks: a source root, or a directory in it, that was replaced (by a symlink, say) while the copy ran is not removed from, and is reported. Without a destination, `-rm` removes the whole source trees. If none of the given destinations can be used (a `-d` glob that matches nothing), nothing is copied or removed (`No valid destination`, 202); a `-di` image that does not exist yet is created first.

`-rf --remove_force` implies `--remove`. **Use with care!** This skips the interactive check requiring user confirmation before removing. If **hpcp** did not generate the correct file list from the specified source paths, hopefully you have fast enough reflexes to press `Ctrl + C` repeatedly to stop all parallel deletion processes if you realize a mistake.

`-b --batch`: Using `-b` with `-rm` will gather the file list for all `source_paths` first, then issue the remove command. This can be helpful because **hpcp** will tune its `-f --files_per_job` parameter accordingly for each task, and running one large remove job might be faster than running many small ones.   -ctl, --command_timeout_limit COMMAND_TIMEOUT_LIMIT
                        Set the command timeout limit in seconds for external
                        commands ( ex. cp / dd ). Default is 0: no timeout.
  -enes, --exit_not_enough_space
                        Exit if there is not enough space on the destination
                        instead of continuing (Note: Default is continue as in
                        compressed fs copy can be down even if source is
                        bigger than free space; without it, a copy that may
                        not fit is tried, with a warning on ext2/3/4, XFS and
                        tmpfs).
