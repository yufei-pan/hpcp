## Questions waiting for the user
Four known-limitation questions from the 9.97 design check of 2026-11-23 (and Q5, from the 9.97 build) (the five deferrals that slipped from version to version since the 9.88 plan; the fifth, the macOS copy check on a network mount, is a build in 9.97). Each is its own question. Nothing in 9.97 waits on them: until an answer, each entry stays in docs/limitations.md as deferred, revisited at the answer. The design check's full reasoning and runs are in the main session's notes (dc997). Who can be hurt in all four: a run into a tree that another local user may write, while that user swaps a directory for a link at the right moment; hpcp's own goal (2026-11-09: "just as fast as possible, trust the user, trust the system. report the error if there is some hardware error instead of slowing down regular operations just for the 0.01% chance") decides what a guard may cost.
- **Q1. `-siff`'s patch apply writes below its target by path: a known limitation?** What the operator sees: a root `-siff` apply whose patch has rows below a directory another user may write can, if that user swaps the directory for a link between hpcp's look and the write, write a file the patch names (with the patch's content, never the other user's) where the link leads; and with `-d /` a link that user put there before the run is followed wherever it leads inside the system, by the apply's own rule (it follows a link that resolves inside the target, on purpose). Why not fix: you decided this on 2026-10-12 (the 9.72 spec, "Decisions (made with the user)", item 2: "Race fix scope. Forced removals only. Ordinary writes keep the documented race."); the 9.88 plan reopened it as a deferral without asking you. The planned fix (a door that follows such a link once) would not close the `-d /` case, and golden-image patches write where users cannot. Revisit when: an operator applies patches as root to trees with rows below directories other users write. Options: **(a) known limitation, as you picked on 2026-10-12 (recommended)**; (b) build it: every write of the apply through the copy's door from the pinned target root, refusing a link met on the way (about ten call sites and the pool's workers; `-d /` still follows a link put there before the run). Your words it touches: none dropped; (a) keeps your 2026-10-12 pick.
- **Q2. A move's directory fsyncs go by path: a known limitation?** What the operator sees: after a root move into a tree another user may write, each directory the move wrote into is fsynced by its path; if that user swaps one for a link during the fsync pass (0.4 to 1.8 s for about 10,000 directories), swaps it back before the copy check, and the machine then loses power within seconds, on a filesystem where a file's own fsync does not already commit its name (on ext4 and XFS it does), moved files may be gone after the power cut. Without the power cut nothing happens; a swap left in place is caught by the copy check (exit 213, every source kept: run in Docker on 9.96). Why not fix: every route through a held descriptor slows or complicates every regular move (the 9.90 build of it was measured 5 to 11 times as long and taken out; an fsync at each directory's finish measured 1.4 to 3.1 s against 0.4 to 0.7 s; one `syncfs` per destination you declined on 2026-11-09). Revisit when: an operator runs root moves into trees others write on storage where a power cut is a real risk, or reports a lost name. Options: **(a) known limitation (recommended)**; (b) build the pool form through a look-only door, measured first. Your words it touches: your 2026-11-09 goal above argues for (a).
- **Q3. Linux without /proc: a node's xattrs and a move's owner-read chmod go by path, and a directory with no owner read stays shut: a known limitation?** What the operator sees, only where /proc is not mounted (a chroot or a stripped container): a root run into a tree another user writes, settling an identical FIFO, socket or device node, sets its `trusted.*` or `security.*` xattrs by path, so a link swapped in at the right moment redirects them; a move's fsync of a 0044 file chmods through a link put at its name; and a runner-owned directory of mode 0207, 0007 or 0047 is not opened to its owner (Permission denied below it; the fix is `chmod u+rx DIR` or mounting /proc). Why not fix: without /proc every regular file's copy already goes by name, which you approved on 2026-11-10 ("Add them to the KL (Recommended)", the entry "Where cp cannot write a file hpcp holds ..."), so guarding a node's xattrs there protects nothing an attacker would pick; the planned fix needs kernel 6.6 or later (`fchmodat2`), so it could not run on EL7 or EL8 at all. Revisit when: an operator runs hpcp as root, with /proc unmounted, into trees other users write. Options: **(a) known limitation, folded into the no-/proc entries (recommended)**; (b) the plan, on kernel 6.6+ only; (c) carry no xattrs to an identical node where there is no descriptor (removes the case, and a working carry with it). Your words it touches: none dropped.
- **Q4. The door goes by path in a directory the runner may not read (the read route): a known limitation?** What the operator sees, only on macOS (and Linux without /proc), only for a non-root run: below a directory the runner may search but not read (another user's 0711 or drop-box 0733 directory, or its own 0300), hpcp goes by path; if the user who may write that tree swaps a directory below it for a link mid-run, the runner's own files land where the link leads, somewhere the runner itself may write. Why not fix: it is the third cause of the same fallback as two you approved on 2026-11-12 (EL7 past 2,048 levels, a process out of descriptors) and Windows (approved 2026-11-11); the macOS fix adds a second kind of hold to the door's four opens, in macOS-only code that CI does not run. This is the closest of the four: RULES says a security hole is always worth fixing, and your approvals of the sibling fallbacks point the other way; the runner can only be led to write where it may write anyway. Revisit when: an operator runs hpcp unprivileged on macOS into trees other users write. Options: **(a) known limitation (recommended)**; (b) build the macOS half: on a refused read open, hold the directory with `O_SEARCH` (tried on the test Mac: `fsync`, `fchmod`, `futimens`, `fsetxattr` and the relative calls work through it, only listing fails), no cost in a regular run; the Linux half stays a limitation either way. Your words it touches: none dropped.
- **Q5. On Python 3.6 where pool workers are spawned (Windows), the live `-pfl` counts do not reach the progress line: a known limitation?** What the operator sees: on Windows with Python 3.6, a `-pfl` listing's progress line shows the counts only as each job returns, not as the workers list; `-F` does reach those workers in 9.97. 9.96 the same. Why not fix: the live counts need a slot per worker that Python 3.6's spawned pool workers cannot be given without more of hpcp's own pool code, for a Python that is end-of-life on a platform hpcp rarely runs on (cas/CLAUDE.md, "Python support"). Revisit when an operator runs `-pfl` on Windows with Python 3.6. Options: **(a) known limitation (recommended; the final review would approve it)**; (b) build it. What waits on it: nothing in 9.97. Your words it touches: none.
