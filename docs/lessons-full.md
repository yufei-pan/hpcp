# Lessons: full entries

Why this project's APIs, formats and agreed behaviours had to change. `lessons.md` has one line per
entry: read that first, and look entries up here by date and name rather than reading this whole. New
entries go last, in the same commit as the change:

```markdown
## YYYY-MM-DD <short name>
- Changed: ...
- Why we had to change: ...
- Original design was wrong because: ...
- Lesson: ...
```

## 2026-11-05 A list of paths names paths, not just files
- Changed: hpcp's -sfl and stdin lists land each path at dest/<path as given>, minus a leading / and any .., the layout `rsync --files-from` and `cp --parents` give (they differ from hpcp in how the directories on the way are treated: hpcp gives a directory it creates its source's mode and owner, and leaves an existing one alone). They used to land by basename.
- Why we had to change: `find src -type f | hpcp -d out` put every file flat, so src/a/x.txt and src/b/x.txt overwrote each other with rc=0, and which one survived varied.
- Original design was wrong because: it fed list entries through the rule for positional arguments, where a basename is what the operator typed. A pipeline's paths carry their directories as information, and the frozenset it read them into lost their order as well.
- Lesson: when a second input route joins an existing one, ask what its input means before reusing the rule. And when two inputs can land on one output, name what the operator meant by each: two named files landing together is a mistake to report, two directories merging is an overlay to honour. Decide the winner once, before any work starts, so no copy mode can answer differently. A rule that compares sources with destinations belongs where destinations are known.

## 2026-11-06 A landing is a path too
- Changed: when a source lies inside the destination and another source would land on it, inside it, or (a directory) on a path that holds it with a file at its place, hpcp names both paths and exits 213 before anything is copied or removed. The first 9.81 build handled only a named file overwritten by a directory's files, and only when two destinations overlapped; a move exited 241 for it.
- Why we had to change: `cd w/D/c; printf '../../c/r\nr\n' | hpcp -d .. -rf` landed one entry on the other entry's source while the second was being copied: 20 runs in 360 left an empty `w/D/r`, with the sources removed and exit 0, and with `-s` or `-nb` one content was always lost. `hpcp d1 d2/d1/ -d d2/ -rf` did the same.
- Original design was wrong because: the settling pass looked at where files land, and ran only when two landings could meet. A landing on a source is not two landings meeting, so the pass never saw it, and a copy that writes a file another copy is reading has no safe order.
- Lesson: for every destination a run writes, ask what else the run reads there. A check on sources against destinations has to cover the destination side of every source, and it runs once before any copy, so every mode refuses the same way.

## 2026-11-06 Judge the thing you protect
- Changed: one rule in `_settle_destinations` replaces `_landing_clash`, `_same_or_inside` and the move-onto-itself loop: a run is refused when a file would land, by real path, on a source file (its own too, in a move), unless, in a copy, that file belongs to a directory that lands on itself. A source that holds the destination leaves it out of its copy, an argument now as a list always did, and `-rme` then checks nothing, because what was left out looks extra, since its copy read files other sources were writing (an empty file, exit 0). `_RealPlaces` gives every check the same real paths. A directory that lands on itself no longer counts as a writer and runs no copy: another source may be writing its files, so even a read for the identity check could fail (exit 190 or 191, 5 runs in 60), while `-rme` still learns what it holds. Forms 7617241 refused now run, forms it let through are refused, and a symlink in the destination that made two list entries one file is a clash (that known limitation is gone).
- Why we had to change: `_landing_clash` compared source roots, by spelling. `hpcp p/q/ -d p/ -rf` lost a file in 120 of 120 runs, because a source was never compared with itself. A link in any path hid the clash, while `_inside_destinations` next to it already compared real paths. And `hpcp */conf -d merged/`, a safe rerun, exited 213, because a directory that copies nothing was still taken for a reader.
- Original design was wrong because: the danger is at file level (a file one copy writes is a file another reads, or a move removes), and a root says nothing about that. Each patch added a case for one shape of root. Its check also looked at what exists (`lexists`), not at what the listing would really copy, so an excluded path could refuse a run.
- Lesson: state the danger in one sentence about the thing at risk, then judge exactly that thing, from the same data the work itself uses. Make it cheap with a gate that proves the expensive question cannot arise, not by asking a cheaper question. A question two checks ask gets one answer, computed once.

## 2026-11-06 A landing never leaves its destination
- Changed: `_source_dest` treats '..' as it treats '.': no name to land under, so the contents land in the destination. `hpcp .. -d out/` used to land in `out/..`.
- Why we had to change: `cd w/sub; hpcp .. -d out/` wrote into `w/sub/` and left `out/` empty, and `cd w/c/s; hpcp ../../x .. -d ../ -rf` swapped two files through it and lost both, in 60 of 60 runs.
- Original design was wrong because: the basename of a source was taken for a name. '.' came out right by accident (joining it changes nothing), and '..' joined as a name climbs out of the destination. `hpcp .. -d out`, without the slash, already gave the contents.
- Lesson: a path part is a name only if it names something. When a layout rule joins user input onto a destination, say what it does with the parts that are not names.

## 2026-11-06 A write goes to an inode, not a path
- Changed: `-co` replaces a destination file that has other hard links instead of writing through it; such a file then has the source's mode, not its old one.
- Why we had to change: `hpcp a/ -d out/ -co -rf` with `ln a/y out/x` wrote a/x into a/y's inode: out/y came out holding X, empty or partial in most runs, and the source was then removed. `hpcp a/ b/ -d out/ -co -rf` with `ln b/x out/y` lost B in most runs.
- Original design was wrong because: `-co` swapped `cp -af` for `cp -f` to keep metadata and lost what `-a` also does: `cp -a` unlinks a destination with several names, `cp -f` opens it. The landing rule works by path, and a hard link has no path to compare.
- Lesson: when an option changes how a file is written, list what the old way did besides the thing the option is about. A check by path protects paths; what shares an inode has to be left by the writer.

## 2026-11-06 Ask the rule that decided, not the spelling
- Changed: a directory named as an argument that is a destination and lands below itself is left out of the run, as a list entry is: `hpcp a b -d b/ -rf` was 241 and is now exit 0, `a` moved, `b` left. `hpcp a -d a/ -rf` was 241 and now moves nothing, exit 0. `-rme` then checks nothing.
- Why we had to change: `hpcp * -d backup/` with `backup` in the working directory gave 0, 213, 213: the first run nests `backup/backup`, and the next run's files land on it. 7617241 gave 0, 0, 0, one level deeper each run.
- Original design was wrong because: leaving out a source that holds the destination covers what it holds, and a source that is the destination holds nothing to copy but itself. It stayed a source that read the files others land on. A prototype that tested the trailing slash away made `a/` look named: `hpcp a/ b/ -d a/ -d out/ -rf` then destroyed a/x. `a/` lands on itself, and 241 stays right.
- Lesson: when a case turns on where something lands, ask `_source_dest` and compare its answer with the destination; never re-derive the rule from the spelling. `a`, `a/`, `.` and `..` differ only in that answer.

## 2026-11-06 'None' and 'could not look' are two answers
- Changed: a landing in a directory that can be neither listed nor searched is refused, exit 213, naming it and `chmod u+rx`. `chmod 000 out; hpcp a/ -d out/ -rf` ran in 9.80 and 7617241. A directory that cannot be listed (0300), or has more entries than the run has names to ask about (past max(10000, files)), is asked by name instead; that also stops one file into a 2M-entry directory from reading all of it (1.04 s, back to about 0.1 s). A listing alone answers too, so `chmod 600 out` runs as in 9.80. A first version refused every directory without search permission, in a probe before the listing: a source with `a/locked` at 600 then gave 0, 213, 213, where 9.80 gives 0, 0, 0, because every folder is asked about and the copy made `out/locked` too.
- Why we had to change: the scan answered "no links" when it failed, so `out/y -> ../b/x` in a 0300 `out` was not seen and the run's own directory sync opened the way: b/x lost in 20 of 20 runs.
- Original design was wrong because: one set meant both "I looked and found none" and "I could not look". And `os.path.islink` turns EACCES into False, the same mistake one level down: only a lstat tells them apart. The scan also read a whole directory for one name, since nothing said how much reading a question is worth.
- Lesson: a look that can fail returns three answers. Bound the look by what the answer is worth, and treat "stopped" the same as "failed": ask a narrower way, open the gate, or refuse with the fix. Refuse only at the question that needs the answer: a look that raises by itself refuses for places nothing lands in.

## 2026-11-06 Clean up what you made
- Changed: a failed copy removes the destination file only when the attempt changed it (inode, size or mtime against before), and a source that cannot be opened gets no `cp` at all. Exit codes stay. The state is the path's own (lstat): a link stays through a failed write, so a retry finishes its target.
- Why we had to change: `os.remove(dest_path)` ran after any failure, so an unreadable source deleted the good copy a backup held. And the last retry returned before it removed its part.
- Original design was wrong because: the cleanup assumed the failure was its own doing. It was written for a part of a file, and a destination that was there before looks the same as a part.
- Lesson: before cleaning up after a failure, prove the failed step made what you are about to remove. And `cp -a` acts on the destination before it opens the source, so only not starting it keeps a hard-linked one.

## 2026-11-06 A node is not its contents
- Changed: under `-co` a source that is not a regular file goes through `cp -af`, so a FIFO, socket or device node is made, as in a plain run, with its mode, owner and times, and never read. A source that would take the name of a device node the destination names itself (`hpcp /dev/sda -d /dev/sdb`, `hpcp a/p -d /dev/sdb`, with or without `-co`; a regular file too when the node has other names) is a clash, exit 213, and the node and the source stay. A plain run replaced the node (exit 200); `-co` read the source into it, or hung.
- Why we had to change: `-co` with a device source read it to its end and wrote it through what was at the destination, another disk if the numbers differed, and a FIFO source hung on the first run. Sending those to `cp -a` alone would have unlinked a device named by `-d`, as a plain run already did.
- Original design was wrong because: `-co` was written for files, and "copy the contents" has no meaning for a node: opening one is an act of its own. And nothing separated a node that is a file of the tree, which a source replaces, from the device the operator named as the destination.
- Lesson: when a flag narrows what a copy does, ask what it means for every kind of source, not only the one it was written for. When moving something to a safer route, ask what that route does to the destination: `cp -a` never reads a node, and always unlinks what is there.

## 2026-11-06 A refusal is as narrow as its reason
- Changed: a device node that `-d` names, and that a source would replace, now takes only that destination out of the job (`_copy_job`). With several `-d` (spill-over) the file lands on the others with a note and the run ends as any other run of that source (a move completes); it is a clash, exit 213, and the job copies nothing only when every destination is such a node. A landing on a name any `-d` gives counts as named (`-d out/ -d out/n`). A patch applied to a directory of a mounted filesystem (`-siff`) is flushed with syncfs too, in a `finally`. A link to a disk counts as the disk; a node for the same device (same kind and number) is no clash; a symlink source, which runs no `cp`, is no clash and keeps 9.81's exit 162. The refusal names the fix. A device source that a user without the right to make nodes cannot copy is refused before `cp -a` takes the old file away, asked by making a node of that kind beside the destination.
- Why we had to change: the first version dropped the whole job when one `-d` was such a node, so `hpcp a/n -d out/ -d dev2` copied nothing where 9.81 landed `out/n`. It judged the destination's name (`lstat`), so a link to a disk was replaced by the source's node, and it called a matching pair a clash. A non-root device copy deleted the old file because `cp -a` unlinks before its `mknod`.
- Original design was wrong because: the reason (one destination is a device) was recorded against the job, which has many destinations, and the check asked what the name is, not what it leads to. And a refusal reasoned from `cp`'s documentation said "would replace it" for cases `cp` never runs in.
- Lesson: keep a refusal at the grain of its reason (per destination, per file), and decide what it covers by asking what the thing leads to (`stat`) and whether the tool runs at all. A permission that decides whether data is lost is asked by doing it (make the node, remove it), before the step that takes the old data away.

## 2026-11-06 A name that matched nothing is still a name
- Changed: a source named as an argument that matches nothing is kept by `_named_sources`, so `verify_src_path` reports it: `hpcp nosuch ok/g -d out/` was exit 0 and is 207, with the rest copied. A move counts it as an error (212, everything kept); `-rme` stops for it by arguments and lists alike. A list entry that is gone does not stop a move: 207 and the rest moves, as in 9.82. A removal with no destination goes on, exit 207. A name excluded with `-e` counts for nothing. A name under a directory that cannot be searched says `cannot be reached`. `hpcp nosuch ok/g` was 70 and is 240. A name with glob characters that match nothing as a pattern is that file, where it was dropped. The last word with no `-d` is held back until the destination is known, so a prompt that turns it down reports it.
- Why we had to change: a mistyped source was dropped with exit 0. With `-rme` that is worse: what the mistyped source holds at the destination looks extra.
- Original design was wrong because: `expand_paths` answers "what matches", and `hpcp()` used that as "what was named", so nothing that matched nothing reached the one check that reports it. And the remove gate counted errors from the copy's start. A first version made a gone list entry stop a move too, so both routes agreed; the user chose otherwise, and rightly: a typed name is a mistake to stop for, a list is older than the tree, and a gone entry has nothing to lose. For `-rme` the two agree, as what looks extra may be what the missing source holds.
- Lesson: when a step can drop what the operator typed, keep it until the step that can report it. Two routes share one answer only when the question is the same; ask what the input means on each. A refusal that names a way out (`-e`) has to honour it.

## 2026-11-06 A name is what the destination reads
- Changed: every landing is folded in memory (`_names_may_fold`, a wide net: NFD, casefold, no ignorable code points). Only when two collide does a run ask, in the directory they land in, with those two names (`_RealPlaces.same_place`, `_one_name`). One name is a clash, exit 213, directory sources and one tree too, where the run was exit 0 with one file's content gone. Each destination of several is asked. A directory that cannot be asked gets a 213 that says so. A directory source is now always listed before the copy, which reuses the listing. `_RealPlaces.is_link` asks by name when a link folds like the landing, so `out/X -> ../src/y` with `src/x` is 213. `-rme` compares what it takes for extra with what the copy wrote by identity, on the names the listing does not show.
- Why we had to change: `a/X` and `b/x` onto a casefold directory lost one, and either could win. With `-rme`, `a/x` onto `out/X` deleted the file from both sides, exit 0.
- Original design was wrong because: `_settle_destinations` compared landings as strings, and `-rme` compared listings as strings. The first fix asked each destination once, up front, "do you fold?", and then applied Python's rules. That gave a false 213 (`Straße` and `STRASSE` on vfat), missed a folding directory or mount below a plain top, could not ask an unwritable top, left a file behind in an append-only directory, and wrote into every destination on every run, all to keep a shortcut that skipped a listing the copy makes anyway. It held that the probe had to come before the shortcut; the listing was free, so the shortcut was the thing to give up.
- Lesson: no single call answers what a filesystem does with a name, and no local rule predicts it. Cast the net in memory, wide, since the filesystem judges what it catches, and ask about the actual pair where it lands. Before keeping a shortcut, price what it saves. Anything that compares names at a destination needs a comparison by identity behind it.

## 2026-11-06 Could not compare is not a crash
- Changed: `copy_file` asks `_known_identical`: a `PermissionError` on either side of the identity check means "not known to be the same". An unreadable source then stops at `_can_open`, exit 190 where it was 191, and the old copy stays. An unreadable destination is copied again, exit 0 where it was 191. Any other read error stays a crash.
- Why we had to change: the identical-file check ran before the readability check, so a rerun with a source gone unreadable ended as `Copy process crashed`.
- Original design was wrong because: a check meant to skip work was treated as one that cannot fail. Moving `_can_open` ahead of it would have added an open per skipped file on every rerun, and catching every `OSError` would have sent an I/O error on to `cp`, which truncates the old copy before its first read.
- Lesson: when a shortcut's question cannot be answered, fall through to the step that owns the failure, and only for the failure that step really handles.

## 2026-11-06 One door for a directory
- Changed: `-nds` makes a directory through `_make_dest_directory`, as the sync does: a file in the way is a clash, exit 213, where it was 70 with a traceback; a directory it cannot make is `Directory sync error`, 193, where it was 70.
- Why we had to change: `process_copy` called `_makedirs` itself, outside every handler.
- Original design was wrong because: "skip the sync" was written as a second way of making the directory, without the checks the sync had.
- Lesson: a flag that skips a step skips what the step changes, not the checks around it. Share the part that stays.

## 2026-11-06 A refusal offers a fix its reader can run
- Changed: a 213 for a place that cannot be searched names the link that led there, what it leads to, and `rm` of it, when that place is on the way to the link's target (`_last_link`, on the failure path only). A link that only spells the way (`alias -> real`, `real/out` mode 000) is not blamed. Exit codes stay.
- Why we had to change: `out/l -> /root/secret/f` said `/root cannot be searched` and offered a `chmod` a user cannot run.
- Original design was wrong because: `_RealPlaces` raised from the walk, which no longer knew the path it was asked about. The public calls now add the link on the way out, so the walk stays as it was.
- Lesson: a refusal states what would let it pass, in terms of what its reader controls. Add that where the question was asked, not where the walk stopped.
- Sharpened 2026-11-10 (9.87, entry 8): the commands a hint gives (the replaced-link Note, the `-ncd` refusal, `rm` and `chmod` of a place that cannot be searched) printed paths as Python holds them: a space split the command, and a name the locale cannot show came out as `\udcXX`, which no shell reads back. They now go through `_shell_word`: as is when safe, else single-quoted, else `$'...'` with octal bytes. Lesson: give the command in a form its shell runs; quote names for the shell, not as the program holds them.

## 2026-11-06 The reason travels with the error
- Changed: a `Task return code error` carries the last three lines of what the tool printed to stderr, after the return code, so `Copy failed` says `No space left on device`. A tool that says nothing keeps the old sentence. The prefix, and so the exit code, stays.
- Why we had to change: a full disk said only "return code 1".
- Original design was wrong because: the runner had the task, and with it the stderr, and passed on only the number.
- Lesson: the layer that sees a tool's own words puts them in the error. Prefixes decide; the words only inform.

## 2026-11-07 Different numbers prove nothing
- Changed: `_one_name` no longer answers "two names" when both names stat as two files: it asks by making them, every time, and only where nothing can be made does a listing answer (both names listed, two names). `-rme` takes an expected name that the listing lacks but that is there for the file under another spelling, by its folded name, not its number. Directories in another spelling (`-rme`), links in another case (`_link_targets`) and a move onto itself, or into its own inside, in another spelling (241) are asked of the directory too. Names that are not valid UTF-8 meet in the net (`replace`), and the directory decides. A 213 that could not ask says why: nothing could be made there (and what fixes that), or the directory refuses the name.
- Why we had to change: exFAT through FUSE, the only exFAT on EL7 and EL8, gives each spelling of one file its own `st_ino`. On a rerun both names were there with two numbers, so round 2's shortcut said two names: `hpcp a/ b/ -d out/ -rf` was 213, then 0 with one content gone; `hpcp X -d x -rf` lost the file; `-rme` deleted what the copy wrote through. A Latin-1 vfat lost one of `\xc9` and `\xe9`, which the net kept apart.
- Original design was wrong because: it took "these two numbers differ" as "these are two files". That holds on every kernel filesystem and fails on any filesystem that numbers names, not files. And the net, which has to be wide because the filesystem judges what it catches, kept apart names it could not read.
- Lesson: an identity check proves sameness, never difference. To learn whether two names are one, ask the filesystem by doing it; an observation (a number, a listing) is only a fallback where nothing can be done, and only in the direction it can prove.

## 2026-11-07 A cheaper filter is no narrower net
- Changed: the check that a file would land on a source file in another spelling folds every file the run reads again whenever the roots meet, as it did before 7da6db0, which folded only the files whose lowercased path lay below a destination.
- Why we had to change: lowercasing is not what any filesystem folds by. A destination reached through a link (`out/d -> ../s/d`) was not below anything, and `s./`, `ς/` for `σ/` and a decomposed `é` did not lowercase alike: `hpcp t/ s/d/F -d out/ -rf` exited 0 on ext4 casefold and lost `s/d/F`, and the copy form wrote over the source.
- Original design was wrong because: a filter put in front of a wide check to save time has to pass everything the check would catch, and this one was a different, narrower rule. Two overlapping 500k trees cost what folding them costs; that is the price of the check.
- Lesson: speed up a safety check by making the check itself cheaper, never by a cheaper rule in front of it that is not a superset of it.

## 2026-11-07 Ask the whole group at once
- Changed: the probe asks a directory about all the spellings the run has of one name there at once (`_ask_names`, which replaces the pair question `_one_name`): it makes each in turn with O_EXCL in one new hidden directory, each file holding its place among those made, and a spelling that is there already is one name with the file that holds it (read from that file, or, where the spelling cannot be looked up, as on vfat, by asking each made name alone). The answer is kept for the run (`_RealPlaces`), and `same_place`, `-rme`'s directories in another spelling, and a key that finds what a file may clash with at once (`_RealPlaces.bucket`) all read it. A probe file that fails for space, quota or an I/O error now says `nothing can be made in DIR to ask it (No space left on device): free some space there and run again`; only EINVAL, EILSEQ and ENAMETOOLONG say the directory refuses the name. An error with no fix of its own ends in `let files be made there` (was `let a directory be made there`). A question about two paths that cannot be asked at one part is unknown there, and the parts after it are not asked. A probe left by `kill -9` holds a small file per spelling.
- Why we had to change: names that are not UTF-8 all fold alike in the net (`replace`), so a tree of 3,000 CP1251 surnames was five groups of about 600 and 902,303 pair probes (87 s, and 40 s on a rerun, against 30 s and 0.3 s with no probe), and `-rme` asked one question 5,001 times for 5,000 directories. A full disk said the directory refused the name.
- Original design was wrong because: the question took the shape of its callers, a pair at a time, so its cost was the square of a group, and how big a group gets is set by how wide the net is, which safety keeps wide. And every error after the probe directory was made was put down to the name.
- Lesson: when a wide net groups candidates for a costly question, ask about the whole group in one go, keep the answer for the run, and read the pairs off it; and a refusal's reason names what failed, the name or the place it was made in.

## 2026-11-07 A net over bytes is cast per byte
- Changed: `_folded` reads a path that is not UTF-8 as a whole name by name, and a name that is not UTF-8 keeps its ASCII and turns every other byte into one mark, where it was decoded with `replace`. A landing on a source file in another spelling that cannot be asked says so (`may land on the source file ...: ... may be one name, and the destination cannot be asked: <reason>`), where it said `which is the source file`. A destination the filesystem will not make is a `Directory sync error`, not a traceback (exit 70).
- Why we had to change: `replace` decodes whatever bytes happen to form UTF-8, so cp1251 `Пё` (CF B8, UTF-8 `ϸ`) and `пё` (EF B8, not UTF-8) folded apart, and on a vfat or exFAT mounted cp1251, koi8-r or iso8859-1 a move, a rename in case and `-rme` each lost a file. The 213 for a landing that could not be asked named a source file as the target and offered no fix.
- Original design was wrong because: the net was meant to be "any byte past ASCII may be any other", and a decoder's partial success is not that rule; a name valid only by chance still gets past it (deferred). The premise itself was short too: the kernel's iso8859-9, iso8859-3 and cp857 tables make ASCII `i` the other case of `İ` (DD, A9, 98), and koi8-ru joins `a` and `p` with bytes past ASCII, so on such a mount `iş.txt` and `İş.txt` were two names to the net and one to the mount, and a move lost one (review round 6). Every letter of such a name, ASCII ones too, is now a mark. Review round 7 found the same for ASCII punctuation: in the kernel's cp932, cp936, cp949 and cp950 a double-byte character can end in any byte from 40 to 7E (``@ [ \ ] ^ _ ` { | } ~`` as well as letters), and kernel exFAT mounted cp932 or cp950 took `xа.txt` (84 70) and `xА.txt` (84 40) for one name, so 40-7E is marked whole; only digits and the punctuation below 40 keep a name apart from others of its length. In the same round, dotless `ı` folds with `i`: casefold keeps it, and a UTF-8 vfat with codepage 850 or 857 gives `kız.txt` the short name `KIZ.TXT`.
- Lesson: when a rule is about bytes, apply it to the bytes; a lenient decoder decides by accident what the rule should decide. And a check that could not tell says that, not the answer it would give if it could. And when the rule is "another table decides", take nothing as fixed that the table could map, ASCII letters included: read the tables (here, all the kernel's nls tables) before saying what is safe to keep.

## 2026-11-07 Check what landed before removing what it came from
- Changed: a move checks each source file and link against its landings before it removes it: one must be there, of its kind, of its size and (unless `-co`) its time, not the source itself, and not one file with another source's landing. A source that fails stays, as a `Destination clash` (213).
- Why we had to change: a move removed every source the copy listed, on the strength of checks made before the copy, which predict from names what a destination will do. Seven rounds of review widened those rules and each found more that a filesystem joins: a vfat 8.3 alias, a legacy charset's other case read as UTF-8 or ASCII, names of different lengths (EUC-JP `ς` and `Σ`). Each lost a content with exit 0.
- Original design was wrong because: a prediction stood in for evidence at the one step that cannot be undone. No rule on names can be complete when the filesystem decides, but what the copy wrote can be looked at, and it costs one `lstat` a file.
- Lesson: before a step that destroys the only copy, check the result it depends on, by what is there (size, time, identity), after the step that made it. The predicting checks stay, to refuse before anything is written; the check after is what makes a miss cost an exit code instead of data.

## 2026-11-07 A mirror judges only what a source speaks for
- Changed: `-rme` judges only below where a directory source lands (all of `out/` for `src/`, `out/b` for `b`), for positional sources as for a list, and never removes what is a source, lies in one or holds one, asked by identity (`(st_dev, st_ino)` of each source, against each extra and the directories above it as named; a link is judged as itself).
- Why we had to change: `hpcp b -d out/ -rme` lands in `out/b` but deleted `out/keep`; `hpcp out/sub/ b/ -d out/ -rme` deleted `out/sub/x`, a source and the only copy of what `b/x` replaced.
- Corrected the same day: the first version also kept a link that leads into a source (`out/d -> ../src/d`), taking it for the source's own copy. That protected nothing (a move that would land on its source is refused before any copy, and the backstop runs after `-rme`) and kept a real extra on every run, so `d` was never mirrored. A link is judged as a link: it is a source only when named as one, and 9.83's removal stands.
- Original design was wrong because: "extra" was computed as "in the destination and not in the copy", over the whole destination, by path. A source says what to copy to one place; it says nothing about the rest of the destination, and a path's spelling in the destination says nothing about what it is.
- Lesson: a cleanup judges only the part a given source speaks for, and asks of each thing it would remove what it is (identity), not where it was found; whatever is a source is never extra.


## 2026-11-07 A tolerance is sized on every filesystem it meets
- Changed: modification times are compared as integer nanoseconds (`st_mtime_ns`), within one step of the coarser of the two, the step guessed as the coarsest of 2 s, 1 s, 10 ms, 1 ms, 1 us, 100 ns and 1 ns that divides the time (`_mtime_step_ns`), and never closer than one float step at that time (238 ns from 2004 to 2038: a time set through float seconds lands within half of it), in the move's backstop, the skip check (`is_file_identical`) and stored states (`states_equal`). A file found identical gets its times again in nanoseconds; hpcp set them through float seconds. Where the time still disagrees but the size matches, the backstop reads the source and its landing to the end, and a landing that holds the same bytes holds the source.
- Why we had to change: the backstop, new in 9.84, turned a time mismatch into a refusal. Times were float seconds, and the step was guessed from the float: near 1.7e9 a float carries about 2.4e-7 s of noise and showed no 1 us or 1 ms step, so moves onto ntfs-3g and lowntfs-3g kept about 400 of 2000 sources and onto udf about 1750, with 213, where 9.83 exited 0. vfat keeps no time before 1980 at all (it sets 315532800), so no tolerance holds such a file.
- Original design was wrong because: the tolerance was written for a check whose miss cost a re-copy, and was reused, unmeasured, by one whose miss refuses the job; a guess from a float cannot see the steps it was meant to find. And a time the filesystem cannot keep is no evidence about the contents. The float guess had also hidden a tolerance of about 200 ns for every time, which a store written through float seconds (hpcp's own skip path among them) relied on: the first strict rule reported such files as changed.
- Lesson: when a check's miss changes from a cost to a refusal, measure its tolerance on every filesystem it will meet; compare what the filesystem stores (integers), not a lossy view of it; and where the cheap evidence cannot exist, ask the expensive question (read) instead of refusing.

## 2026-11-07 A guard takes the operator's words, not a filter's output
- Changed: `-rme`'s source guard is built from the sources as named, before the list entries inside a destination are left in place (`_inside_destinations`), and answers by identity once a directory: the walks never follow a link, so a stat of each directory they found answers for all below it, a file is stat'ed only in a directory that holds a file source, and no link is followed: a link is judged as itself. A link that lies in a source, and a named link that leads nowhere, are sources too.
- Why we had to change: `printf 'out/b/sub/f\nb\n' | hpcp -d out -rme` said "Skipped 1 list entries inside the destination", then removed `out/b/sub/f`, its only copy, with exit 0: the guard never saw the entry the filter had taken out. And it took a realpath (an lstat of each part) and a stat for every extra: on NFS with actimeo=0, 52 s for 10,000 extras where the walk that found them took 0.35 s.
- Original design was wrong because: the guard was fed the list the copy works from, which by design lacks what the copy leaves alone, and that is exactly what the guard protects. And it asked per path what is known per directory.
- Lesson: a safety check takes its input from what the operator said, before any step that narrows it for another purpose; and it asks each question at the level its answer lives at (a directory's identity once), not once per thing below it.

## 2026-11-08 A write never goes into what is there
- Changed: a copy onto an existing landing writes a new name beside it (`.hpcp_tmp_` and 16 random hex digits) and renames it over the landing once whole; a FIFO, socket, device node or link below a destination is replaced, never opened or written through; a directory below a destination goes through one door (`_dest_directory`) that replaces a link or node by a real directory, with a note for a link. Only what `-d` names is followed and written through, as `cp` follows its destination argument. `-co` writes beside too and carries the old file's owner, group, mode, `user.*` xattrs, ACLs, SELinux label and FAT bits (a new inode).
- Why we had to change: `cp` was handed the landing and decided what to do with what was there: it truncated an old copy before its first read, so a source failing mid-file (a real EIO on EL7) cost the last good backup; it waited forever on a lone FIFO; it wrote a file into the disk behind a device node in the tree; it wrote through a planted link, so a user who could write the destination could steer a root restore into `/etc`. Each had its own guard (`_leave_hard_links`, `_remove_what_failed`, a serial scan of every landing directory for links), and none closed them.
- Original design was wrong because: a copy tool was given the name of something that may hold the only good copy, or may be a way somewhere else, and every guard answered one thing the tool might do to it. Never giving the tool what is there removes all of them at once.
- Lesson: give a copy tool a new name, not the landing; replace what is there once the new file is whole; follow and write through only what the operator named.

## 2026-11-08 In place only after the source has read to its end
- Changed: the fallback where the beside route fails (no new name, a refused rename, no room) writes in place only a regular file with one name, only once the source has just been read to its end (the temporary file got all of it, or hpcp reads it through), and only when the rewrite needs no space it does not free, or no data was written beside and the free space holds the source. Anything else keeps the old copy (190), and a FIFO, node or link that cannot be replaced is refused (213), never written through.
- Why we had to change: the design's first fallbacks wrote in place wherever the beside route failed; the review showed that brought entry 1 back (a 0555 directory and a failing source: the old copy at 0 bytes; a growing rewrite with no room beside: the old copy gone) and wrote through a link and hung on a FIFO in a 0555 directory.
- Original design was wrong because: a fallback to the old behaviour inherits the old behaviour's losses; it has to prove the conditions under which the old route is safe.
- Lesson: a fallback that writes into the old copy first proves that the source reads whole and that the rewrite needs no space it does not have; anything else keeps the old copy, and what cannot be replaced is refused.

## 2026-11-08 A stop is a cleanup
- Changed: SIGINT, SIGTERM and SIGHUP run Ctrl-C's cleanup (KeyboardInterrupt, so multiCMD stops `cp` in its own process group and every `finally` runs) in the main process and every pool worker, except a signal the process was started ignoring; the main process passes a stop on to its workers and, after the cleanup, ends by SIGTERM or SIGHUP with the default action (SIGINT keeps 130). A worker's parent-death watch watches the main process by its sentinel and sends SIGUSR2, hpcp's own, to its main thread before it exits.
- Why we had to change: with temporary files, a stop that skipped the `finally` left them: SIGTERM to the main process left four complete 128 MB ones, SIGINT to the group three partial ones (the watch called `os._exit` before multiCMD had stopped `cp`). `_thread.interrupt_main` would run whatever SIGINT's disposition is, and under `sh -c '... &'` on EL7 that is SIG_IGN, a TypeError. Under forkserver a worker's parent is the fork server, which outlives the main process, so getppid never changed.
- Original design was wrong because: a stop by any signal but SIGINT was taken to need no cleanup, which was true only while nothing was left half made; and the watch asked about the wrong process.
- Lesson: every process that can leave a temporary file turns each stop it can catch into its cleanup path and then ends as the signal asked; a signal it was started ignoring stays ignored; a watch that sees its parent gone stops the main thread with a signal of its own, and watches the process that matters, not its own parent.

## 2026-11-08 A link below a destination is a name
- Changed: a symlink below a destination is replaced by what the source has there (a file or a directory), with a note naming it and the `-d` form that writes through it; under `-ncd`, or where it cannot be removed, the files below it are refused (213). `_link_targets`, `_RealPlaces.links`, `is_link` and the serial listing of every landing directory are gone; a landing below a destination resolves by `lstat`, unfollowed. The move's backstop counts a link at a landing as what it leads to only when the operator named it.
- Why we had to change: 9.80 to 9.84 wrote through such a link (another place took the files and the source's mode, and as root its owner), and the checks that predicted where each write would go had to scan every landing directory, refused a directory they could not read, and still missed what the kernel would do.
- Original design was wrong because: following a link in a tree made every check predict where each write goes; replacing it leaves nothing to predict.
- Lesson: a link below a destination is a name of the tree, not a way; replace it, say so, and let the operator name it to write through it.

## 2026-11-08 Only a directory holds what lies below it
- Changed: a move places a removal below a source root only when that root is a real directory (`lstat`), so `lb/x` named beside the link `lb` is a root of its own, opened through the link by its path; named links are removed after everything else. A path listed through a link that another source copies as a link is a clash (213).
- Why we had to change: `hpcp lb lb/x -d out/ -rf` placed `lb/x` below `lb` by its spelling and then opened `lb` with `O_NOFOLLOW`: ELOOP (192) at random, and `b/x`, which the operator named, never removed.
- Original design was wrong because: containment was read from the spelling; a spelling that puts a path below a link or a file says nothing about what holds it.
- Lesson: ask what a root is before reaching through it, and remove a link after what was reached through it.

## 2026-11-08 A special the operator names is a source
- Changed: a FIFO, socket or device named as a source (an argument or a list entry) is copied as `cp -a` copies it, exit 0, and moved with `-rf`; one met in a tree is still skipped with a note.
- Why we had to change: the listing said "not a file or directory" (200) for a named FIFO yet listed it, so the node was made and the run failed, and `-rf` kept every source (212); `-s` already exited 0.
- Original design was wrong because: a refusal by type, which belongs to a walk that meets a special, was applied to a name the operator typed.
- Lesson: a refusal by type belongs to a walk; what the operator names is what they asked for.

## 2026-11-08 A probe costs only its names
- Changed: the probe that asks a directory about names makes them relative to descriptors (`mkdir(dir_fd=)`, then the probe's own descriptor), and the node probe with `mknod(dir_fd=)`.
- Why we had to change: made at the probe's full path, the question failed with "File name too long" for a landing within about 57 characters of PATH_MAX, a false 213 where the copy itself fits.
- Original design was wrong because: the question was made longer than what it asks about.
- Lesson: make what you ask a directory about relative to its descriptor, or the question fails where the answer would not.

## 2026-11-08 A rename is not a barrier
- Changed: a rewrite's temporary copy is fsynced before it is renamed over the old copy (the core and the patch apply), and a move writes its copies to disk before it removes a source (first built as one syncfs of each destination filesystem; see 2026-11-09); a sync that fails removes nothing.
- Why we had to change: XFS does not flush a file renamed over another (ext4's `auto_da_alloc` happened to), and neither filesystem writes a file's data before journaled renames and unlinks reach the disk. After a power cut a rewrite could leave the landing empty with the old copy gone, and a move could lose both the copy and the source. The build host was hard-reset four times in two weeks.
- Original design was wrong because: it took old-or-new for granted from the rename alone ("hpcp fsyncs neither way"), which holds for a crash of the process, not of the machine.
- Lesson: a rename orders names, not data; fsync before renaming over what must survive, and before removing what a copy replaced.

## 2026-11-09 Check a write while its data is still held
- Changed: a move fsyncs each landing in the worker that copied it, right after the copy, and reports the file copied only then; a landing whose fsync fails is a failed copy (removed, so a rerun writes it again) and stops the move's removal through the existing copy-failure gate. The first build of 9.85 synced each destination filesystem once, at the end (syncfs).
- Why we had to change: (1) before Linux 5.8 syncfs reports no write error at all, and the main targets run 3.10 (EL7) and 4.18 (EL8): on a thin volume out of space, syncfs returned 0 where an fsync of the same file returned EIO, and the move removed its source with exit 0 (checked on both). (2) A writeback error is kept only on the in-memory inode; in a long move the kernel writes early landings back on its own, long before any check at the end, and an inode evicted under the copy's own memory pressure takes its error with it, so a syncfs followed by an fsync of each landing can miss errors in a big move; an fsync right after the copy, while the data is still dirty and the worker's own descriptor holds the inode, cannot. (3) The destination root's filesystem is not every filesystem the copies land on (a mount below it), and a directory opened for syncfs must be readable (a write-only destination failed with 212).
- Original design was wrong because: it asked the question once, at the end and from the outside, of a kernel that answers only what it still remembers, and trusted a call that on the target kernels cannot say no.
- Lesson: check a write while its data is still held: fsync each file right after writing it, on its own descriptor, and treat a failure as a failed copy; an fsync of a new file on ext4 and XFS also commits the transaction that made its name and every earlier one, so no directory fsync is needed there.

## 2026-11-09 A safe route that cannot always run is as safe as its fallback
- Changed: a rewrite is written in place again by default (`cp` writes the file the worker holds open, so the inode stays), as 9.84 did; 9.85's write beside and rename is used by default only where a write in place could corrupt (a file with other names, one that cannot be opened for writing, a FIFO, device or link at the landing), and for every rewrite with `-wb`, with no fallback (what cannot be made, filled or renamed beside keeps the old copy, 190); `-rbw` reads the source to its end before a write in place. The in-place fallback is gone: `_write_over`, the room reservation, the hole punching, and 9.86's first build's filesystem allowlist and reflink checks.
- Why we had to change: the new inode on every rewrite dropped what a filesystem keeps on the inode (a Lustre or GPFS layout, `chattr` flags, a project id), gave NFS readers `ESTALE`, left `.nfsXXXX` files that `-rme` saw as extras, and cost an fsync a rewrite (about 1 to 1.5 ms a file on EL7). Every place the rename cannot run (a 0555 or sticky directory, a bind-mounted file, no room for a second copy, `-co` metadata) needed a fallback that wrote in place, and each review round of 9.85 and 9.86's first build found a new way for it to lose the old copy: holes, reserved room given back, copy-on-write filesystems, overlay and NFS naming the wrong filesystem, a reflinked XFS file. In each, plain `cp`, 9.84's route, had kept or finished the file.
- Original design was wrong because: it made every rewrite pay, in inode identity and time, against failures that are rare and reported (a source failing part way, a stop, a full disk: exit 190, the source kept). And a route that cannot always run is only as safe as the fallback it needs; that fallback second-guessed the filesystem, and the filesystem was right more often.
- Lesson: before making a safer route the default, list every place it cannot run and say what happens there; if the answer is a fallback that does the old thing more cleverly, keep the old thing as the default, use the safe route where the old one could corrupt, and offer it everywhere as an option. Protect against a rare, reported failure with an option, not by changing every write.

## 2026-11-09 A path we resolve ourselves skips the kernel's checks on the way
- Changed: a link the operator names with `-d` is followed only where the kernel follows it for this run (asked by a `stat` through it). A link it refuses (`fs.protected_symlinks`: another user's link in a sticky world-writable directory such as `/tmp`) is kept, exit 190, `... is a link to TARGET, which cannot be followed (Permission denied)`, as 9.84's `cp` refused it; 9.85 wrote through it, exit 0. A dangling link and a link in a loop behave as in 9.85.
- Why we had to change: 9.85 resolved a named link with `os.path.realpath` and gave `cp` the resolved path, so that hpcp could look at the file behind the link. The kernel applies `fs.protected_symlinks` while it follows a link; `realpath` only reads the link, and the path it returns has no link left in it. A root run then wrote through a link another user had planted (found by the 9.86 review, checked in Docker: 9.84 exit 190 and nothing written, 9.85 exit 0 and the target overwritten).
- Original design was wrong because: it took over a step the kernel does, and with the step dropped a check the kernel makes only there, without asking what the step carries besides its result.
- Lesson: before doing in our own code what the kernel does on the way to a file (following a link, walking a path), list the checks it makes there (`fs.protected_symlinks`, search permission, an LSM); let the kernel do the step, or ask it first by doing the real thing once.

## 2026-11-10 A directory's metadata goes on after its contents
- Changed: the folder sync makes each destination directory and gives it only what does not stop writes into it: stale xattrs removed and the source's set, the owner, and the mode, plus owner read, write and search for a non-root runner that owns it. A finish pass after the files, the links and `-rme` gives it its times, exact mode and BSD flags through one descriptor, deepest first (one pool, a barrier per depth). Each step sets only what differs, so a clean rerun sets nothing on a directory that already matches.
- Why we had to change: 9.86 copied each directory's mode and times (`shutil.copystat`, then `os.utime`) before any file went in. A non-root copy of a 0555 or 0444 directory holding files exited 190 with the directory empty, a rerun the same; and every directory that got a file, a link or a subdirectory afterwards kept the copy's time (3 of 7 directories on Python 3.14, 5 of 7 on 3.6, in a probe), until a rerun with nothing to copy put them right.
- Original design was wrong because: it treated a directory as a file whose metadata can go on at any time, when what is written into a directory changes its times and its mode decides whether anything can be written.
- Lesson: make a directory with what lets its contents in, and give it its times, exact mode and flags after them, deepest first (as `cp -a` and rsync do): a parent's mode set later can shut its owner out of the child.

## 2026-11-10 A space check counts the work it will do
- Changed: `-enes` still compares a source's listed (allocated) size with the destinations' free space first. Only where that does not fit does it count what the copy will write: one `lstat` of each file and of its landing at the first destination holding one; nothing for a landing of the same size whose time agrees (any time under `-co`), what the source takes beyond the old copy for a rewrite in place, and the whole file for a new file or a rewrite beside the old copy. The source is skipped (228) only when the free space is below that count.
- Why we had to change: a rerun onto a nearly full destination skipped every source whose listed size exceeded the free space, though nothing needed copying (a 3 MB file copied onto a 5 MiB tmpfs, then rerun with `-enes`: 228; without `-enes` the rerun exits 0).
- Original design was wrong because: it asked whether the source fits, when the question is whether the work fits; on a rerun most of the source is already there and takes no new room.
- Lesson: a check that refuses for lack of room counts the room the run will take: what is not already there and the same, less what a rewrite in place frees. Keep the cheap total as the first test, so a run that clearly fits pays nothing for the count.

## 2026-11-10 A child writes the parent's held file through its own inherited descriptor
- Changed: `cp` gets the file hpcp holds (a rewrite in place, and since 9.87 a first copy and the beside route's new file, which hpcp makes with `O_EXCL`) as a descriptor it inherits (multiCMD 1.59's `pass_fds`), named `/proc/self/fd/N` on Linux and `/dev/fd/N` on macOS. Whether it works is asked once a run, by doing it, in the parent (as it opens a copy pool), which hands each worker the answer, so no worker makes a temporary file for an early Ctrl-C to leave (40 of 2,100 early Ctrl-Cs on Python 3.6 left an `hpcp-held-probe-*` file when each worker asked): `cp`, with the run's flags, copies a 1-byte temporary file holding `c` onto a held temporary file holding `ab`, and what the held file then holds is the answer: `c` (written, and left at the source's size), `cb` (written through a reopen that does not truncate: hpcp empties the held file before each `cp`), anything else or a failure (no route: `cp` gets the name, as 9.84). On Linux only GNU `cp` is asked: BusyBox's makes every destination anew, and uutils' `cp` 0.10 writes the held file but sets no mode or times through it.
- Why we had to change: 9.86 named the worker's `/proc/PID/fd/N`. That works only on Linux, and only where `/proc` shows the worker to `cp`: not from a PID namespace whose `/proc` is an ancestor's (`unshare -p -f` without `--mount-proc`: there PID is another process, so 9.86 gave the name), not for a worker `/proc` refuses. macOS has no `/proc`; its `/dev/fd/N` reopen is a `dup` of the same open file, which ignores `O_TRUNC` and shares the offset, so a working open says nothing about what the copy leaves. And first copies and the beside route's new file went to `cp` by name, so a link put at the name in that moment was written through by a root run.
- Original design was wrong because: it reached the parent's descriptor through a name that depends on what another process may see, when the child can simply be handed the descriptor; and its probe (`cp /dev/null` onto a descriptor of `/dev/zero`) asked whether the open works, not what a real copy leaves in the file.
- Lesson: to have a child write a file you hold, pass it the descriptor and let it name its own (`/proc/self/fd/N`, `/dev/fd/N`); ask once by doing the real thing on a scratch file and reading back what it left, since the reopen may be a `dup` that ignores the open's flags. A route that writes the data but not the metadata (uutils' `cp`) is no route. A file you make for the child gets its owner after the data, as `cp -a` gives it: given first, the write is charged to that owner's quota (XFS counts a root write against the file's owner; a user at the hard limit got Disk quota exceeded where 9.86 completed), so first only where a default ACL's entries would be narrowed away.

## 2026-11-10 A look again is judged as the first look was
- Changed: what no look at a landing lets through is one function, `_judge_landing`, which `_cp_once` calls at its first look and after every later one: a dangling link the operator named (190), a link the kernel will not follow for this run (190), and a directory (213, `Destination clash: DIR is a directory, not copying SRC over it`). 9.87's builds judged the first look only.
- Why we had to change: 9.87 made a first copy with `O_EXCL`, and a name that appears at the landing after the look makes the create fail and the landing be looked at again. That second look skipped the guards: as root, a dangling link planted at a named landing made hpcp create the file where it points and exit 0 (9.86's `cp` refused it, 190), and a directory planted there was copied into, through a link inside it (9.86 did the same). Found by the 9.87 review A in Docker with a hook between the look and the create.
- Original design was wrong because: the guards were written inline in the function that took the first look, and the retry loop added later took its own look with its own, shorter, rules.
- Lesson: a retry that looks again judges with the same function the first look went through (LESSONS.md: two code paths answering one question will disagree); put the rules in the one function every look calls, and test the retry with each thing the first look refuses.

## 2026-11-10 A pool sized by what it waits on keeps a floor, and the CPU count is only a ceiling for CPU work
- Changed: a move's default `-j` is `max(16, CPU count)`; a copy's stays one a CPU. 9.87's first build used 4 workers a CPU for a move (never released), because each worker waits on its files' fsyncs.
- Why we had to change: on a 32-CPU host with a fast disk, 128 workers made a move of 2,000 files of 4 KiB 20 % (Python 3.14) to 45 % (3.6) slower than 32, and a move of 100 files 0.60 s against 0.32 s on 3.6, which starts every worker of a pool at once. The builder had measured only 2- and 4-vCPU VMs with slow disks, where 4 a CPU is 8 and 16 workers.
- Original design was wrong because: the number of fsyncs the disk wants in flight is a property of the disk, not of the CPU count, and a multiple of the CPU count grows with a property that has nothing to do with the wait.
- Lesson: size a pool that waits on a device by a floor measured on the slow case, and never below the number the version before gave; scale with the CPUs only where the work is CPU; test the default on both a small and a big host before taking a multiple.

## 2026-11-10 A list of file names holds each name's own bytes
- Changed: `changes.tsv`, the manifest and a `-tdfl` list are written and read with the filesystem's encoding and its error handler (`sys.getfilesystemencoding()`, `sys.getfilesystemencodeerrors()`), so each name's own bytes (`os.fsencode`'s) are in the file, whatever the locale. `disk.tsv` holds tool output (labels, GPT names), which multiCMD decodes as UTF-8, and stays UTF-8.
- Why we had to change: 9.86 wrote UTF-8 and read UTF-8, which round-trips a name as text but not under the C locale (a name's non-UTF-8-decodable bytes became surrogates that UTF-8 encodes to other characters: UnicodeEncodeError on 3.6 with LANG unset). 9.87's first fix read the names with `os.fsdecode` and left the writers at UTF-8, on the premise that UTF-8 with surrogateescape writes the bytes `os.fsencode` gives under any locale. It does only where the filesystem encoding is UTF-8 or ASCII: under Latin-1, EUC-JP or KOI8-R `listdir` gives `\xe9` as U+00E9, which UTF-8 writes as `c3 a9`, and the reader's `fsdecode` read that as two characters: a patch made and applied under one Latin-1 locale was refused (`Incomplete patch: payload missing or unsafe`, nothing applied; 9.86 applied it). Found by the 9.87 review C on CentOS 7. A patch made by 9.86 under such a locale holds UTF-8 where 9.87 now reads the locale's bytes: refused when it has a payload for the name, and a deletion of the name in a patch with no payload for it is skipped as already done. Under UTF-8 and C nothing differs.
- Original design was wrong because: it chose the file's encoding on one side only, and checked the round trip under the locales the bug was seen in (C), not under one whose encoding is neither UTF-8 nor ASCII.
- Lesson: a file that holds file names holds each name's own bytes, written and read with the same filesystem encoding; a text encoding of our own round-trips only where it equals the filesystem's. Test the writer and the reader together under a locale that is neither UTF-8 nor ASCII (Latin-1), and keep tool output, which is text in an encoding of its own, apart from names.

## 2026-11-10 An empty argument is a question, not a path
- Changed: `-d ''` is no destination given (`Destination path not specified, using ...`), as in 9.86; 9.87's first fold of `-d` (`os.path.normpath`, for `l/../out`) turned `''` into `.`.
- Why we had to change: `hpcp a -d ''`, the likely result of `hpcp a -d "$DEST"` with `DEST` unset, copied `a`'s contents into the working directory without the question 9.86 asked (`do you want to continue?` at a terminal, `using ...` off one); with two sources both were "copied" onto themselves there.
- Original design was wrong because: the fold ran on every `-d` before the code that knows an empty one means "not given", and `normpath('')` is `'.'`.
- Lesson: a normaliser of a path argument skips the empty one (it is the absence of an argument); the code that asks about it gets it unchanged.

## 2026-11-10 A crash is the failure of the source it crashed on
- Changed: a crash inside one file's copy (`Copy process crashed`, exit 191) is recorded as that source's failure (`_copy_failed`), as every other `Copy failed` line is, and a landing that keeps changing is `Copy failed` (190), not a crash. A landing below a directory the runner cannot search is `Copy failed` (193) again, as in 9.86 (the free-space question falls back to the nearest parent that answers, for any OSError).
- Why we had to change: the copy check after a copy (and before a move's removal) leaves out only the sources that recorded a failure. A crash printed its line without recording it, so the check then said the source had been copied but was at none of its landings (`Destination clash`, 213) beside the crash (191). 9.86 had the gap; 9.87's earlier changes put new paths into it (an unsearchable directory, a landing that kept changing).
- Original design was wrong because: failure was two things, a printed line and a recorded fact, and the catch-all handler did only the first.
- Lesson: every way out of a per-file step records the failure for that file in the one place the later checks read (a catch-all handler too), so no later check reports on a file that never got its answer.

## 2026-11-10 A reader keeps reading what earlier releases wrote
- Changed: a change list of a patch whose manifest names an hpcp before 9.87 (`hpcp_version`) is read as that release read it: its bytes as UTF-8, spelled by this locale (`_utf8_name_line`); where this locale cannot spell that (LANG unset on Python 3.6), the line's own bytes. A list 9.87 wrote is read with the filesystem's encoding, as it was written.
- Why we had to change: 9.87 wrote each name's own bytes and read every list that way. A patch 9.86 made under a Latin-1 locale holds `c3 a9` for the name `e9`; 9.87 read it as two characters, so a row with a payload was refused (`Incomplete patch`), and a deletion was skipped as already done: `skipped 1`, exit 0, the file left on the target, where 9.86 deleted it. Found by the 9.87 final review on CentOS 7 (`en_US.iso88591`).
- Original design was wrong because: it changed the writer and the reader together and tested only pairs made and applied by one build; patches are kept (increments of a backup), so the reader meets files of every earlier writer.
- Lesson: when a file format's writer changes, the reader decides by who wrote the file (a version the file already carries), and reads each as its writer wrote it; test a file made by the release before against the new reader, under a locale that is neither UTF-8 nor ASCII.

## 2026-11-10 A guard over imports is scoped to the imports, and released on every path
- Changed: hpcp's module-level imports (its import header, with `resource`, and from multiCMD 1.60 its embed) run with SIGINT blocked in the importing thread, inside a `try` whose `finally` lets it in again, only where it was not blocked before; a Ctrl-C meanwhile is raised there. `_fat_ioctl_numbers` reads `os.uname()` instead of `platform.machine()`, so importing hpcp runs no subprocess. A program that imports hpcp now gets a Ctrl-C pressed during `import hpcp` at the header's end (about 30 to 45 ms into the import on Python 3.7), not where it lands; a program with other threads that take SIGINT is as before. 9.87's limitations entry had planned a recording handler only when hpcp runs as the program, never when imported: a mask installs no handler, so that plan's reason (a library caller keeps its own handlers) still holds.
- Why we had to change: a Ctrl-C while Python imported hpcp was raised by Python's own handler inside importlib's weak-reference callbacks (a module lock's `cb`; 3.12+ also `KeyedRef.remove`), which drop it (`Exception ignored in: ...`): the run went on and exited 0, with `-rf` to its removal (1 in 3,000 early Ctrl-Cs through pip's launcher on 3.7 and 3.14). On 3.6 to 3.8 hpcp's module body also ran `uname -p` through `platform.machine()`, and a Ctrl-C was dropped in that `Popen.__del__`. The plan's first design blocked SIGINT for the whole module, with the release at its end: a failure anywhere in 14,600 lines (a missing `lzma` for the embed) left SIGINT blocked for the importing program, because a `try` cannot span a module's definitions.
- Original design was wrong because: it guarded a span by where it starts and ends, not by a block that owns both ends; and it left work in the module body (a subprocess) that the guard was then stretched to cover.
- Lesson: a guard (a signal mask, a lock) taken at module level covers only the statements it exists for, gathered into one `try` whose `finally` releases it, so a failure inside cannot leave it held; move what the guard must cover into that block, and what it need not cover out of the import entirely.

## 2026-11-10 Store what C made before Python can raise
- Changed: every file hpcp makes and must clean up (a first copy's landing in `_cp_made`; the held-file probe's two files in `_held_route`) is made by `_create`, which appends the new descriptor to a list by C (`list.extend(map(functools.partial(os.open, flags=..., mode=...), (name,)))`); the caller's cleanup closes and removes what the list holds. `_held_route` no longer uses `tempfile`: it tries tempfile's own candidate directories in tempfile's order (`tempfile.tempdir` alone when a program set it; else `TMPDIR`, `TEMP`, `TMP`, `/tmp`, `/var/tmp`, `/usr/tmp`, the working directory), makes the probe's source there, and its held file with `O_TMPFILE` (no name), falling back to a name it unlinks at once, as `tempfile.TemporaryFile` does; each name goes as soon as it has served. `_MAKING`, 9.87's flag that made `_stop` only record a stop while such a file was made, is gone.
- Why we had to change: a signal's handler runs at the first instruction after a C call returns, so `fd = os.open(...)` can lose the descriptor between the create and the store, and the file stays (empty, mode 0600, at a first copy's landing). 9.87 deferred hpcp's own handler there, but a program that imports hpcp and keeps Python's own Ctrl-C handler was not covered: in a probe that stopped `_cp_made` 2,000 times with Python's handler, 9.87 left 525 of 1,219 stopped calls' files on 3.14 (most of the call is the create) and 9.88 none. `tempfile`'s own calls had the same window inside the standard library (`gettempdir`'s test file, `mkstemp`'s name), which no flag of hpcp's could cover for another handler: 9.87 left files in 1,980 and 1,465 of 2,000 stopped probes with Python's handler. And a cleanup in a `finally` that the run reached normally can itself be cut by the first stop, so a name is removed in the normal path as soon as it has served, the `finally` covering only the paths a stop or an error took first.
- Original design was wrong because: it guarded a window by telling the one handler it controls to wait, where the window was one Python itself opens for every handler; and it took a standard-library helper whose internal windows it could not reach.
- Lesson: hold a resource C made before Python can run another instruction (a C call that stores it: `list.extend` over `map`), never through an assignment a handler can land before; clean up only what the stored handle proves you made; and remove a name as soon as it has served, not only in a `finally` that the first stop can cut.

## 2026-11-10 Key work by where it lands, not where it comes from
- Changed: `sync_directories_parallel_batch` and `sync_directories_serial_batch` (public) build one list of folder syncs in job order, each job's root then its listing, and keep one per destination directory, the last (`_last_per_destination`): a directory that several jobs share (merged sources, `hpcp a/ b/ -d out/`, or `hpcp a/ b -d out/` with `a/b/` there) is synced once, from the later source, as a merged file is ("replaced by a later source"), and each returns one record for it; before, every job's sync ran and returned its record, and the parallel batch synced each root twice (its own, and as the first folder of its listing). The finish compares a directory's time within the filesystem's step (`_mtimes_agree`, the file rule), not exactly.
- Why we had to change: with two records for one directory every rerun set its mode and times twice and its ctime moved each run; in a pool which source's metadata won was not fixed, and with `a/ b` the earlier source's folder (synced in the pool after the roots) won over the later source's root. On vfat (2 s), exFAT (10 ms) and HFS+ (1 s) the exact compare set every directory's times on every rerun. Found by the 9.87 review B (F6); the spec check found the root-and-folder case (B7).
- Original design was wrong because: it keyed the work by where it came from (a source directory, a job) when what is done to the destination is decided by where it lands; two sources that land on one directory are one directory, and a job's root is one of its folders.
- Lesson: key work that writes a destination by the destination (its absolute path), decide once which source wins for each, the way the files already decide it, and count the root among the folders; compare what a filesystem stores with the tolerance the filesystem keeps, everywhere the same value is compared.

## 2026-11-10 A mode that shuts the runner out is set after every step that looks below it
- Changed: in a move by a non-root runner, a directory whose exact mode takes its owner's search (0607, owner `rw-`) gets owner read and search added at the finish (`_first_mode`), and its exact mode only after the move's removal step, ran or skipped (`_finish_late`, deepest first, each fsynced through its own descriptor). A stop before that leaves such a directory with owner read and search until a rerun. `_shut_to_its_owner` is replaced by `_synced_at_finish` (guarded for platforms without `os.geteuid`).
- Why we had to change: 9.87 gave the directory its 0607 at the finish, and then the move's own steps reached below it by path: the directory fsync of `d/sub` met EACCES and was reported as `Copy failed: the directory ... cannot be written to disk`, exit 212, every source kept, with the copy whole. The deferral's plan (fsync every directory at its finish) moved the failure on to the move's check of its landings (213). 9.87's guard also called `os.geteuid()` for every directory a move synced, which Windows does not have (reasoned from the code).
- Original design was wrong because: it set the final mode at the one step whose job is the metadata, without asking which later steps of the same run still need to look through that directory.
- Lesson: before a step sets a permission that takes the runner's own access, list every later step of the run that reaches through the object, and set it after the last of them (deepest first), leaving a stop's partial state at the wider, recoverable mode.

## 2026-11-11 A destination the operator named is pinned for the run
- Changed: hpcp() records each destination named with `-d` that is a directory when the copy starts, as named (a link followed): its device and inode (`NAMED_IDS`, handed to the workers with the run's settings). Each process's door (`_dest_directory`) checks the destination against it as it opens it; one that leads to another directory now is refused for everything below it: `Destination clash: DEST now leads to another directory than the one this run started writing in: not copying FILE; run hpcp again to write where it leads now` (213), printed once a process and recorded for every file, so a move keeps those sources. A destination the run makes later is pinned by each process's own open.
- Why we had to change: 9.88's door holds every directory below a destination by descriptor, but each process opened the destination itself by name, and on Python 3.14 (Linux, forkserver) and macOS (spawn) every worker opens it fresh. In a root run into a destination inside a user's own directory (`-d /home/alice/restore/`), that user could swap `restore` for a link to `/etc/cron.d` after the run started, and the workers that opened it later wrote there as root. The user chose "Pin it (Recommended)" (the 9.88 plan's Q2).
- Original design was wrong because: "a named destination is followed, as cp follows its destination argument" was decided for one open (cp's), but a run opens it many times, in many processes, over hours; following it at every open let whoever can rename it choose where a root run writes.
- Lesson: resolve a place the operator named once, when the run starts, and have every later open check that it still leads to the same object; follow a link as named, but only to what it led to then. A refusal repeated for every file is said once a process and counted for each.
